# 电源键拦截分级方案设计（挂机键语义）

> 文档性质：**设计稿（待审核）**。固化「电源键拦截」的三种分级方案与目标行为。
> 关联文档：
> - 《电源键拦截实施总结.md》—— 当前已上线的「纯消费模式」实现细节与排障记录（本文档的现状基线）。
> - 《挂机键拦截方案设计文档.md》—— 早期 ENDCALL+无障碍拉回方案，已被 evdev grab 方案取代，不再采用。

---

## 1. 目标行为定义（术语约定）

本文档中「挂机键」特指**物理电源键（KEY_POWER，keyCode=116）**，在诺基亚语义下被重定义为「红键/挂机键」：

| 场景 | 用户按挂机键后期望行为 |
|------|------------------------|
| 屏幕亮 + 处于任意应用（微信、设置等） | **回到本应用主界面（诺基亚桌面 `NokiaDesktopActivity`）**，不熄屏 |
| 屏幕亮 + 已处于诺基亚桌面主界面 | **锁屏（熄屏）** |
| 屏幕灭 / 已锁屏 | **唤醒（点亮屏幕）** |

即：**按下挂机键不退出应用，而是回到本应用主界面；在主界面再次按下挂机键进行锁屏。**

> 与普通安卓 power 键（熄屏/唤醒）的核心差异：power 键被重定义为「回桌面 / 锁屏」双态键，熄屏、唤醒只是该语义的副作用，不再由系统默认处理。

## 2. 三种方案分级总览

| 方案 | 权限条件 | 其它键（音量键等） | 目标行为 | 注入通道 | 状态 |
|------|----------|--------------------|----------|----------|------|
| **方案一** adb + uinput | shell 可写 `/dev/uinput` | **正常**（uinput 原样回放，不吞键） | 完整实现 | uinput 回放 + shell 注入 | **待实现、待在有权限机验证** |
| **方案二** adb 无 uinput（保底） | shell 仅可 `EVIOCGRAB` | **被吞**（已知缺陷，即当前副作用） | 完整实现 | 仅 shell 注入 | 当前纯消费模式基础上增强 |
| **方案三** root | root 完整权限 | 正常，能力最强 | 完整实现 | 待定（uinput / 系统级） | **暂缓（预留扩展点）** |

关键结论：
- **三种方案共享同一套「目标行为决策逻辑」**（回桌面 / 锁屏 / 唤醒），仅「非 power 键事件」的处理不同（回放 or 吞掉）。
- 方案一与方案二的目标行为**完全一致**，唯一区别是音量键等其它键是否被吞 —— 这正是用户可接受范围内「有权限体验更好」的体现。
- 注入不依赖 uinput：`am start` / `input keyevent` 为 shell 权限命令，方案二无 uinput 也能实现完整目标行为。

## 3. 统一架构

### 3.1 总体链路

```
物理挂机键(power) 按下
      │
      ▼
mini_shizuku 服务端(原生层 interceptor.c)
  ├─ find_device_with_key(KEY_POWER) → 找到含 power 的设备(本机 event5/qpnp_pon)
  ├─ EVIOCGRAB 独占抓取（系统 InputReader 收不到该设备事件）
  ├─ 尝试 setup_uinput()
  │     ├─ 成功 → 回放模式：非 power 事件原样回放到 uinput（不吞键）
  │     └─ 失败 → 纯消费模式：非 power 事件一并丢弃（保底）
  │
  └─ power 事件 → 【目标行为决策状态机】→ 注入
        ├─ 屏幕灭      → 注入唤醒（input keyevent 224 / 26）
        ├─ 屏幕亮+非桌面 → 注入回桌面（am start 拉起 NokiaDesktopActivity）
        └─ 屏幕亮+桌面   → 注入锁屏（input keyevent 26）
```

### 3.2 决策输入（状态探测）

服务端以 shell 身份执行 `dumpsys` 获取两个状态，由独立「状态线程」轮询缓存（避免按键时现场执行造成延迟）：

| 状态 | 命令 | 解析目标 | Android 4.4 输出示例 |
|------|------|----------|----------------------|
| 屏幕状态 | `dumpsys power 2>/dev/null` | `mWakefulness=Awake/Asleep` | `mWakefulness=Awake` |
| 前台窗口 | `dumpsys window windows 2>/dev/null` | `mCurrentFocus=Window{... 组件名}` | `mCurrentFocus=Window{41f1bd08 u0 com.android.launcher/...}` |

- 前台判断：解析 `mCurrentFocus` 中组件名的**包名前缀**，命中 `io.github.cctyl.nokia` 即为本应用（兼容 debug 后缀 `.debug` 与 release 无后缀）。
- 轮询频率建议 500ms；按键事件到达时直接读缓存，注入延迟 ≈ 0。
- 兼容性风险：各 Android 版本 `dumpsys` 输出格式有差异（4.4 / 5+ / 13），解析正则需按版本容错，实机验证为准。

### 3.3 注入通道

| 动作 | 注入方式 | 说明 |
|------|----------|------|
| 回桌面 | `am start -n <pkg>/ru.playsoftware.j2meloader.nokia.NokiaDesktopActivity` | 精确拉起，**不依赖 HOME 归属**（比 `input keyevent 3` 更可靠） |
| 锁屏 | `input keyevent 26`（POWER） | 走 InputManager，不受 evdev grab 影响，触发系统锁屏+熄屏 |
| 唤醒 | `input keyevent 224`（WAKEUP），备选 `26` | 灭屏时注入点亮屏幕；不同 ROM 对注入 power 唤醒支持度不一，需实机验证 |

> 设计决策：**注入统一走 shell 命令**（`am start` / `input keyevent`），方案一、方案二完全复用同一套注入逻辑；uinput 的唯一职责是**非 power 键事件回放**（解决吞音量键），职责单一、逻辑干净。

## 4. 目标行为决策状态机（核心逻辑）

服务端拦截线程在收到 `power 键按下(DOWN)` 事件后执行（power 的 UP 事件一律消费丢弃）：

```
power DOWN 到达（已被 grab 拦截）
  │
  ├─ 读状态缓存：屏幕是否亮 + 前台是否本应用
  │
  ├─ 屏幕灭(Asleep)
  │     → 注入唤醒：input keyevent 224   （点亮屏幕，显示锁屏/桌面）
  │
  ├─ 屏幕亮(Awake) + 前台非本应用
  │     → 注入回桌面：am start -n .../NokiaDesktopActivity
  │
  └─ 屏幕亮(Awake) + 前台是本应用
        → 注入锁屏：input keyevent 26    （触发系统锁屏+熄屏）
```

要点：
- **双击防抖**：注入间隔离 1s 以上，避免与系统 power 防误触策略冲突导致注入被忽略。
- **长按处理（风险项）**：grab 后系统长按 power 的关机菜单将失效。可选增强：检测 DOWN 后超过 2s 未 UP 视为长按，此时释放 grab 放行原始事件（参考 KeyMapper 的 10 秒安全兜底思路），作为可选迭代项，首版可不做。
- **状态缓存失效兜底**：若 `dumpsys` 解析失败（异常输出），保守默认按「屏幕亮 + 前台非本应用」处理（回桌面，最不易造成困在锁屏）。

## 5. 方案一：adb + uinput（推荐，有权限机）

### 5.1 前提
- 设备 shell 可写 `/dev/uinput`（`setup_uinput()` 成功）。

### 5.2 行为
- **非 power 键事件**：原样回放到 uinput 虚拟设备（`virtual-nokia-keypad`），音量键等行为完全不变（当前 `interceptor.c` 已实现该分支）。
- **power 键事件**：进入决策状态机（第 4 节），注入回桌面 / 锁屏 / 唤醒。

### 5.3 与现状代码的差异
现状 `interceptor.c` 已具备 uinput 回放框架，仅需改造 `interceptor_run()` 事件循环中 power 分支：
- 现状：power 事件 → 直接 `LOG("Power key consumed")` 丢弃。
- 改造：power DOWN → 调决策状态机 → `popen()` 执行注入命令；power UP → 丢弃。

### 5.4 待验证点（有权限机验证，最大风险）
- [ ] 该机 `setup_uinput` 是否真正成功（日志出现 `uinput replay device created`）。
- [ ] 回放后音量键行为是否与 grab 前完全一致。
- [ ] 注入 power(26) 锁屏 / 注入 224 唤醒在目标 ROM 是否生效。

---

## 6. 方案二：adb 无 uinput（保底，当前方案增强）

### 6.1 前提
- 仅能 `EVIOCGRAB`，无法写 `/dev/uinput`（当前 Android 4.4 设备即此情形）。

### 6.2 行为
- **非 power 键事件**：无法回放，一并丢弃（**已知缺陷：吞音量键，与当前版本一致**）。
- **power 键事件**：与方案一**完全相同**的决策状态机 + shell 注入，目标行为完整实现。

### 6.3 说明
- 这是「无权限但目标行为不妥协」的兜底：用户核心诉求（挂机键语义）在方案二下**可完整达成**，代价仅为音量键失效。
- UI 应明确提示当前模式（「保底模式：音量键将被占用」），避免用户困惑。

---

## 7. 方案三：root（暂缓，预留）

- **当前不做**，仅保留扩展点。
- root 后能力升级方向（供后续设计）：
  1. 直接获得 `/dev/uinput` 写权限 → 能力等同方案一；
  2. 可修改 `.kl` 键位映射把 KEY_POWER 重映射，从源头改变语义；
  3. 可系统级注入（`service call` / InputManager 通道），实现长按关机菜单保留等更完整行为。
- 架构上预留：`InterceptorNative` 原生层方法签名不变，root 方案只需替换/增强 `setup_uinput` 与注入实现，不影响 Java 层与 UI。


```bash

```

### 9.3 状态一致性
- 设置页开启后显示真实模式（回放/保底），重启服务端后状态查询与实际一致（依赖 `INTERCEPTOR_STATUS`）。

## 10. 风险与自动容错策略

> 本表列出的技术风险**均由实现端自动处理**（代码容错 + 保守兜底），无需用户做技术判断。
> 实现时按「多路尝试 + 失败兜底」原则：一种方式不行自动换另一种，全部失败则执行最保守、最不易造成不良后果的行为（回桌面）。

| # | 风险 | 实现端自动容错策略 |
|---|------|--------------------|
| 1 | 注入 `26`（锁屏）在部分 ROM 无效 | 注入失败/无响应时自动补试 `224`、`am` 组合等备用方式；首版上线前在目标机实测一次确定最有效方式并写死 |
| 2 | 注入 `224`（唤醒）在部分 ROM 无效 | 同上，备用 `26`；两路都无效时保守处理（不重复注入） |
| 3 | `dumpsys` 输出格式各版本差异 | 解析正则按已知版本（4.4 / 5+ / 13）各写一版自动匹配；全部解析失败时默认「屏幕亮 + 非桌面」→ 回桌面（最安全） |
| 4 | 长按 power 关机菜单失效 | 首版接受（与目标行为不冲突）；后续做「长按 2s 放行」增强，不影响本版 |
| 5 | 系统 power 防误触忽略快速连按 | 注入自动节流 ≥1s，代码内置，无需配置 |
| 6 | debug / release 包名后缀差异 | 前台判断统一用包名前缀 `io.github.cctyl.nokia` 匹配，两端自动兼容 |
| 7 | 锁屏后桌面进程可能被系统回收 | 桌面为 singleTask + HOME，唤醒时系统自动重启它；如实测变慢再补保活 |
| 8 | 方案二吞音量键（无 uinput 无法回放，不可消除） | 非技术问题，属已知取舍：UI 明确提示当前为「保底模式」及音量键影响 |

### 10.1 需要用户配合的事（仅使用层面，无技术判断）

1. **提供一台有 uinput 权限的机器**（你已表示可以找）—— 用于验证方案一「不吞音量键」。
2. **装好后做几个简单操作并把现象告诉我**（每个方案验证约 2 分钟）：
   - 打开任意应用（如设置）→ 按挂机键 → 是否回到诺基亚桌面？
   - 在诺基亚桌面 → 按挂机键 → 是否锁屏？
   - 锁屏后 → 按挂机键 → 是否亮屏唤醒？
   - （方案一机器额外）按音量键 → 音量是否正常？
   - 关闭「挂机键拦截」开关 → power 键是否恢复系统默认行为？
3. 其余技术问题（注入方式、解析容错、节流、包名匹配等）**全部由实现端处理，你无需关心**。

## 11. 验收标准

1. 【方案一】有 uinput 权限机：任意应用按挂机键回诺基亚桌面；桌面再按锁屏；锁屏后按唤醒；**音量键全程正常**。
2. 【方案二】无 uinput 机：**上述目标行为完全一致**；音量键被吞但 UI 明确提示当前为保底模式。
3. 关闭「挂机键拦截」开关后，power 键恢复系统默认行为。
4. 设置页可查询当前模式（回放 / 保底），与真实服务状态一致。
5. 连续按键 20 次无崩溃、无注入风暴；开关状态不漂移。

## 12. 里程碑建议

1. **Phase 1**：完善 `interceptor.c` 决策状态机 + 状态线程 + 注入（方案一、二共享逻辑）+ `prepareLibrary` bug 修复 + `INTERCEPTOR_STATUS`。
2. **Phase 2**：在无 uinput 的 Android 4.4 设备验证方案二全链路（回桌面/锁屏/唤醒）。
3. **Phase 3**：拿到有 uinput 权限机后验证方案一（音量键不吞 + 目标行为）。
4. **Phase 4（可选）**：长按放行、root 方案设计。
