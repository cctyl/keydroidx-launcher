# 发布前回归测试清单

> 适用产品：原键桌面（`keydroidx-launcher`）
> 用途：每次发版前，照这份清单把主要功能走一遍，避免"上次改了 A、这次崩了 B"。

**先说清楚三件事：**

1. **这份清单只写"该看到什么"，不写"按哪个键码"。** 因为每台手机的按键映射都不一样，具体发什么键由执行者照《AI按键操作手册》先查出来。清单里一律用「左软键 / 右软键 / 确认键 / 方向键上、下、左、右 / 返回键」称呼。
2. **凡是和"设备上装了什么"有关的（应用数量、图标、第几页），一律写成相对说法**（"右上角页码为准""高亮落在目标上"），不会写死"第 3 格""第 2 页"——因为换台手机就不一样。
3. **每个编号在报告里都要有状态**（通过 / 不通过 / 未测）——具体规则（未测怎么交代、禁止什么写法、条目分级）统一见第六章 6.0 节，不在前面重复。

### 执行顺序（按"第一次用这台手机"的自然流程排）

重装 debug 包后是全新安装，应用自己会带你走首启流程——所以测试顺序照这个自然流程排：先测"安装后自动发生的事"，再测日常功能。

1. **第 0 步 · 重装**：按上面「测试版本」卸载并重装 debug 包。
2. **第 1 步 · 首启向导**：第一次打开应用，走【启动-01】——自动弹配键向导：按键机选左软键「绑定」逐项录 9 个键，触屏机选右软键「触屏模式」（不绑键）。向导细节另见【设置-向导-01】。
3. **第 2 步 · 权限授予**：核心权限在首启收尾时会被引导（【启动-01】第 5 步、【启动-02】），随后进「桌面设置 → 系统与权限 → 系统权限自检」把该授的都授齐（【设置-权限-01】）。
4. **第 3 步 · 默认桌面**：把本应用设为系统默认桌面（【启动-01】第 4 步的询问、【设置-07】）。
5. **第 4 步 · 其余用例**：从第三章起按编号顺序执行（桌面 → 功能表 → 应用程序 → 桌面设置 → 其它界面与系统行为 → 第六章补充）。

三个必要的例外（都是正文里已有提醒的收拢，不是改顺序）：

- **mini_shizuku 激活（【mini_shizuku-02/03】）尽量紧跟在第 2 步之后做**——后面大量用例（冻结、亮度、清理后台、最近任务、电源键拦截）都依赖它在线，别等到用的时候才发现没激活。
- **电源类里的重启 / 重启到 Fastboot（【桌面-17】②③）放在本轮最后测**，会打断后续流程；关机 / Recovery 本轮不测。

### 3.1 待机屏（桌面）

> 待机屏就是按 Home 键回到的那个界面，也是整个桌面的门面。它的特征是**底部左边写「功能表」、右边写「桌面设置」**。

#### 【桌面-01】待机屏长什么样

**这条测什么**：桌面主界面的基本外观，后面所有测试的起点。

**从哪开始**：手机已解锁，按一下 Home 键。

**应该看到，从上往下依次是**：

1. **最顶上一行是状态栏**（单行，详见【桌面-02】）。
2. **中间主区域，从上到下依次是**：
   - 一块**大时钟区**：左上是**运营商名**、下面是**大号时间**；右侧两行是**公历日期**和**星期 · 农历**。运营商在这里，**只在待机屏显示**；
   - 一排**快捷栏图标**（带半透明深色通栏托盘底，左右无边界，可能没有图标）；
   - 一条**通知条**（没开通知权限就整条不显示）；
   - 一堆**组件小方块**（日历、内存、存储这类，可能一个都没有）；
   - 最下面一排**快捷开关图标**。
3. **最底下一行分三格**：左下角「功能表」，中间**空着**（待机屏不显示页面名），右下角「桌面设置」。

**通过标准**：底部同时能看到「功能表」和「桌面设置」= 你现在确实在待机屏。

**反例**：底部中间写着「功能表」→ 你已经进了功能表页；满屏大时钟 → 那是锁屏界面。

**我的依据**：《AI按键操作手册》第 3.1、3.2 节（已实测）；顶栏布局来自 `keydroidx_top_bar.xml`；时钟区与托盘来自 `fragment_keydroidx_desktop.xml` 的 `clockPanel` 与 `bg_keydroidx_shortcut_tray.xml`。

#### 【桌面-02】顶栏显示的是不是真实系统状态

**这条测什么**：顶部状态栏是不是真的在反映手机当前状态（而不是写死的假图）。

**从哪开始**：待机屏。

**应该看到**：

- **状态栏（单行，图标左右分摊）**：左边是信号（插一张卡显示「1」+ 信号格；双卡显示「1」「2」两组），信号格数随真实信号强弱变化；**中间是时间（绝对居中）**；右边依次是 WiFi、蓝牙、飞行模式图标（**只有开着的时候才显示**，没开的看不见），电池贴最右。图标全开挤压到时间时，时间会自动平移让位——任何图标组合下时间都不与图标重叠。
- **运营商名不在状态栏**：在待机屏大时钟区、大号时钟的**上方**（**只在待机屏显示**，功能表/应用程序页看不到运营商名，属设计如此）。
- 没插卡的卡槽显示「无SIM」；开了飞行模式时显示「飞行模式」（都显示在时钟区的运营商位置）。

**怎么做（挑两三个验证一下，不用全测）**：

1. 把手机 WiFi 打开 → 顶栏 WiFi 图标出现；关掉 → 图标消失。
2. 开飞行模式 → 时钟区运营商位置变成「飞行模式」，信号格变成无信号。
3. 等一分钟 → 右下角时钟跟着走。

**通过标准**：顶栏跟着系统实际状态变，不是固定不动。

**需要什么条件**：信号部分需要电话权限（首次进桌面会弹权限申请）；没有 SIM 卡时只能验证"无SIM"这条。

**我的依据**：`StatusBarController`（运营商逻辑：无 SIM → 「无SIM」、飞行模式 → 「飞行模式」；电量走 `updateBatteryFromIntent()`；运营商视图在桌面时钟区，`refreshCarrierViews()` 在碎片重建后重绑）；`keydroidx_top_bar.xml`；`KeydroidxBatteryDrawable`（电池图标怎么画的）。

**顺带一起测：电池图标的变化**

电池图标**不是系统图**，是桌面自己画的：一个白色描边的电池外壳 + 右边一个小突起（正极）+ 里面 **4 格**电量条。下面是它**唯一**的判定规则：

| 情况 | 点亮几格 | 格子颜色 | 有闪电吗 |
|---|---|---|---|
| 电量 > 75% | 4 格 | 绿 | 无 |
| 50% ~ 75% | 3 格 | 绿 | 无 |
| 25% ~ 50% | 2 格 | 绿 | 无 |
| 11% ~ 25% | 1 格 | 绿 | 无 |
| **≤ 10%** | 1 格 | **红** | 无 |
| **正在充电**（不管剩多少电） | 按上面的格数算 | **亮绿** | **有（黄色闪电）** |
| **省电模式**（电量 > 10%） | 按上面的格数算 | **黄** | 无 |
| 省电模式 + 正在充电 | 按上面的格数算 | **黄** | **有** |

**三条要记住的规则（最容易记错的地方）**：

1. **红只有一种情况**：电量 ≤10% 而且**没在充电**。
2. **充电就变亮绿 + 加一个黄色闪电**，哪怕只剩 5% 电也是亮绿，不是红。
3. **省电模式的黄色盖得住绿、盖不住红**（≤10% 还是红），也**盖不住闪电**（省电 + 充电 = 黄色格子配黄色闪电）。

**怎么模拟（不用真把电耗完、也不用真插充电器）**

前提：手机连着电脑、adb 能用。模拟只影响显示，不会真的充电或耗电。**每换一种情况，先执行一次 `adb shell dumpsys battery reset` 再设**，避免上一步的状态残留。

1. **模拟高电量**：`adb shell dumpsys battery set level 90` → 回桌面看：4 格全绿。
2. **模拟低电量告警**：`adb shell dumpsys battery set level 8`，再 `adb shell dumpsys battery unplug` → 1 格、**红色**、没有闪电。
3. **模拟充电**：`adb shell dumpsys battery set ac 1` → 格子变**亮绿**、出现**黄色闪电**。想再看"半电充电"的样子，接着执行 `adb shell dumpsys battery set level 50`。
4. **模拟省电模式**：`adb shell settings put global low_power 1` → 格子变**黄**；这时如果充电模拟还开着，闪电应该仍然在。
5. **测完必须还原**（不然系统会一直以为你在充电、电量只有 8%）：`adb shell dumpsys battery reset`，再 `adb shell settings put global low_power 0`。

**如果模拟完桌面没反应**：把桌面切走再切回来（按 Home，或者进功能表再退出）——顶栏在每次回到桌面时会重读一次电量。

**通过标准**：对照上表，每种情况的"格数 / 颜色 / 有没有闪电"三项都对得上。

**需要什么条件**：能连 adb。部分机型不允许 `dumpsys battery set`，命令报错的话就改用真的充电器（看充电态）和真的耗电（看低电量红格）来测。

**别混淆**：低电量时**系统自己**也会弹省电提示、系统状态栏也会有自己的变化，那些跟桌面无关。

**你要重点看的地方**：见附录 C 的 C1（顶栏各项位置是否如你所愿）；电池的上面这套规则是我从代码里读出来的，真机对不上就告诉我。

#### 【桌面-03】方向键在待机屏上怎么走

**这条测什么**：待机屏四个区域之间焦点怎么跳。这条最容易把"正常"当成"坏了"。

**从哪开始**：待机屏。第一次按任意方向键时，高亮会先落到第一个可选项上。

**应该看到的规律**：

| 按键 | 会发生什么 |
|---|---|
| `下` | 从上一区往下一区走：快捷栏 → 通知条 → 组件区 → 快捷开关栏；走到最下面再按 `下`，会**绕回最上面** |
| `上` | 反过来往上走，走到最上面再按会绕回最下面 |
| `左 / 右` | **只在"快捷栏"和"快捷开关栏"这两排里横向移动，到头会绕回本排另一头**；在**通知条**和**组件区**里按左右**没有反应**（它们是竖着一列的） |

**通过标准**：上下能跨区走、左右在横排里绕圈、在竖排区里按左右不动。

**千万别当成 bug**：在组件区按左右键"没反应"是故意的，因为组件区就是一列，不存在左右。

**我的依据**：`KeydroidxDesktopFragment` 的 `moveUp/moveDown/moveLeft/moveRight`。

#### 【桌面-04】顶部快捷栏（放常用应用的那排）

**这条测什么**：待机屏顶部那排快捷应用图标能不能用。

**从哪开始**：待机屏顶部。如果顶部没有图标，说明还没配快捷应用——先去「桌面设置 → 桌面内容 → 顶部快捷栏设置」勾几个。

**应该看到**：

- 方向键 `左 / 右` 在本排内移动高亮，**高亮到一个图标时会浮出它的应用名**（气泡在图标**上方**弹出、贴着托盘顶边，大约 2 秒后消失）。
- 按**确认键**启动这个应用。
- 如果启动的是 J2ME（JAR）应用，会进入 J2ME 的运行界面。
- 如果这个应用被冻结了，会**先自动解冻再启动**。

**通过标准**：高亮移动时浮出应用名；确认键能把应用打开。

**空态**：一个快捷应用都没配时，这块显示「（无快捷应用）」。

**顺带测：怎么加、怎么删、顺序怎么定**

配置入口在桌面设置里：待机屏 → 右软键「桌面设置」→「桌面内容」→「顶部快捷栏设置」。

**加一个**：进上面那个页面 → 高亮想加的应用 → 按确认键 → 方框从 `[ ]` 变成 `[✓]`（顶部「已选」数字 +1）→ 按右软键「返回」回待机屏。

**应该看到**：顶部快捷栏多出这个应用，而且**排在这一排的最后面**。

**删一个**：同样的路径进去 → 高亮那个已经勾上的应用（方框是 `[✓]`）→ 按确认键取消（变回 `[ ]`）→ 返回待机屏。

**应该看到**：这个图标从顶部消失。

**顺序是怎么定的**：完整规则见【设置-快捷栏-01】——一句话版：这个页面**没有排序功能**（没有选项菜单、没有「调整排序」，别去找；有排序的是**桌面组件设置**和**快捷开关设置**），顺序 = **勾选先后**，新勾的排最后；想调顺序只能全部取消后按目标顺序重勾。

**通过标准**：加/删立刻反映到待机屏顶部；新增项出现在最末尾。

**需要什么条件**：设备上已装应用（或已装 JAR）。

**我的依据**：`KeydroidxDesktopFragment`（快捷栏构建与启动、名字气泡）；`KeydroidxShortcutSettingsFragment`（勾选即持久化、顺序为 `LinkedHashMap` 的插入顺序）；`KeydroidxSettingsStorage`（快捷栏配置存成有序列表）。

#### 【桌面-05】通知条

**这条测什么**：桌面快捷栏下面那条"未读通知"提示。

**从哪开始**：待机屏。

**应该看到**：

- 有通知时：显示「N 条未读通知 · 最新一条的标题：内容」。
- 没有通知时：显示「暂无通知」，铃铛图标变成静音样式。
- 按**确认键**进入通知中心页。

**关键规则**：这条通知条**只在一个前提下才显示**——「桌面设置 → 系统与权限 → 通知中心」里的「桌面显示通知条」打开、**并且**已经授予通知使用权。两个条件差一个，整条都会隐藏（不是显示空的）。

**通过标准**：满足条件时能看到并进得去；不满足条件时整条不显示。

**怎么造测试通知（不用干等别人给你发消息）**

用项目里的脚本 `scripts\notify.ps1`（详细说明见 `scripts\README.md`）：

```powershell
cd scripts
.\notify.ps1 -Count 3      # 连发 3 条测试通知
# 回待机屏看通知条：应该显示「3 条未读通知 · 最新一条的标题：内容」
.\notify.ps1 -List         # 确认手机当前确实有几条
.\notify.ps1 -Clear        # 尝试清空（不可靠，失败会打印手动清理的办法）
```

- **测"有 N 条"和"只显示最新一条"**：连发几条（`-Count 3`），条数和"最新一条"都会跟着变。

**我的依据**：`KeydroidxDesktopFragment` 的 `refreshNotifBar()`；通知脚本 `scripts\notify.ps1`。

#### 【桌面-08】后台管理组件（最近任务）

**这条测什么**：桌面上显示"后台有几个任务"，进最近任务页，并且清得掉。

**先搞懂它读的是什么（不然没法判断对错）**

这个组件读的是**系统记录的"你打开过什么"**（系统 recents），**不是"哪些进程还活着"**。所以：进程已经死了、但记录还在的应用，**照样会被列出来——这是正常的，不是 bug**。

**结论：测试必须分两步走——先造出已知的一批任务，再拿系统自己的记录当"标准答案"对照。** 不然列表可能是空的，或者混着以前打开过的应用，你根本不知道哪个数字才算对。

**第 0 步 · 先建立干净起点**

进「最近任务」页 → 左软键「选项」→「清理全部任务」，直到列表清空、组件数字归零。
如果提示「可清理的应用都已被保护」，说明有卡片在保护名单里：在那张卡片上按「选项」→「取消保护」（已保护的卡片，菜单项会从「保护此应用」变成「取消保护」）。

**第 1 步 · 造 3 个已知任务**

在电脑上跑（脚本 `scripts\recents.ps1`，说明见 `scripts\README.md`）：

```powershell
cd scripts
.\recents.ps1 -Seed "com.android.settings,com.android.deskclock,com.android.calculator2"
```

包名换成你机器上真实存在的应用；查包名：`adb shell pm list packages | Select-String 关键字`。

**第 2 步 · 读"标准答案"**

```powershell
.\recents.ps1 -List
```

它打印的就是**系统当前记录的任务清单**——也正是桌面要读的那份数据。

**第 3 步 · 和桌面比对**

- 按 Home 回待机屏 → 组件右侧应该显示「N 个任务」，N 与上一步打印的条数**一致**。
- 按确认键进「最近任务」页 → 卡片里**必须能看到刚才打开的那几个应用**，并且**最近打开的排在最前面**。

**第 4 步 · 清理验证**

回到最近任务页 → 按数字键 0（或「选项」→「清理全部任务」）→ 提示「已清理 N 个任务」→ 卡片清空。
再回待机屏：组件数字归零 / 显示空态；再跑一次 `.\recents.ps1 -List`，系统记录也应该空了。

**第 5 步 · 白名单（保护名单）验证：受保护的真的清不掉吗**

承接第 1 步造的 3 个任务（如果第 4 步已经清完，重新 `-Seed` 造 3 个）。下面假设三个任务是 A、B、C。

**5.1 打上保护**：最近任务页高亮 B → 左软键「选项」→「保护此应用」。

**应该看到**：提示「已保护"B"」；**B 卡片预览区右上角出现一个绿色盾牌角标**；再开一次选项菜单，这一项变成了「**取消保护**」（图标换成开锁）。

**5.2 批量清理，看它挡不挡**：按数字键 0（无二次确认）。

**应该看到**：提示「已清理 2 个任务」——只清了 A 和 C。

**判定（核心）**：

- B 卡片**还在**，盾牌角标还在；A、C 消失；
- 回待机屏，组件数字 = **1**；
- 再跑 `.\recents.ps1 -List`：系统记录里**只剩 B**（A、C 的记录已被删）。

**5.3 保护挡不挡"手动清理"（反向验证，重点，千万别当成 bug）**：高亮 B → 选项 →「清理此任务」。

**应该看到**：确认框里**比平时多一行**「该应用在保护名单中，本次为手动清理。」——按右软键「清理」后 B **照样被清掉**。这是**设计如此**：保护名单只挡**批量清理**（数字键 0 / 「清理全部任务」），**挡不住对单个应用的显式清理**——「清理此任务」和数字键 5 都算手动清理，同样不受保护限制、同样没有二次确认。

**5.4 解除保护**：重新造 3 个任务并给 B 上保护 → 选项 →「取消保护」→ 提示「已取消保护"B"」→ 盾牌消失 → 按 0 清理 → 三个全清掉、归零。

**5.5 边界：全部都被保护**：把列表里剩下的任务全部上保护 → 按 0 → 提示「**可清理的应用都已被保护**」，列表一个不少。

**通过标准（四条都要满足）**：

1. 我打开的那几个应用**必须出现**在卡片里；
2. 组件数字与 `-List` 打印的条数**一致**；
3. 清理后：卡片、组件数字、系统记录**三者都归零**；
4. **白名单**：批量清理只清未保护的（受保护的卡片和系统记录都还在）；手动清理不受保护限制、且确认框多出保护提示行；全部被保护时提示「可清理的应用都已被保护」；盾牌角标与「保护此应用 ↔ 取消保护」菜单文案随状态正确切换。

**如果 mini_shizuku 没激活**：组件显示「未激活」，页面显示「未激活 mini_shizuku」+「去激活 mini_shizuku」按钮。这是预期表现，不是故障。

**需要什么条件**：Android 5.0+ 需要 mini_shizuku 已激活才能读出真实任务；Android 4.4 直接可读，不需要特权。

**我的依据**：`KeydroidxRecentTasksHelper`（数据来源、以及"最近任务 = 用户打开过的东西"这个口径）、`KeydroidxRecentTasksFragment`（清理走 `clearSingleTask`：force-stop 之外还会删掉系统任务记录；保护名单持久化于 `KeydroidxSettingsStorage`、重启不丢；绿色盾牌角标画在卡片预览区右上角；批量清理跳过保护名单、手动清理不受限；各提示文案）、`scripts\recents.ps1`。

#### 【桌面-12】快捷开关栏总览：19 种开关

**这条测什么**：待机屏最下面那排开关。一次覆盖全部类型。

**从哪开始**：待机屏最下面一排。**开关也不是自带的**，要自己去勾：「桌面设置 → 桌面内容 → 快捷开关」。

**怎么判断开关是开是关**（两处一起看）：

- **图标**：它本色是**白色**的。**开**的时候完全不透明，看着就是**纯白**；**关**的时候透明度降到约三分之一（35%），白被压淡，在深色底上看着就**发灰发暗**。（所以不是"颜色从灰变成白"，而是同一个白，一明一暗。）
- **小圆点**：**开 = 蓝色**（亮蓝）、**关 = 灰蓝色**（偏蓝的深灰，不是纯灰）。

**特例**：**亮度**开关的图标**不随开关变淡**（恒定全不透明），它的状态由图标本身表达（低 / 中 / 高 / 自动四档）——不然最暗那档会被压得几乎看不见。

**⚠️ 这几种开关的小圆点"不作数"**：**一键冻结 / 一键解冻 / 清理后台 / 一键锁屏**，以及**四个电源开关**——它们的小圆点**永远是灰的**（代码里这几类的"开状态"恒为 false）。判断它们成没成功，只能看弹出来的提示文字，或者用下表最后一列的命令核对，**别看着灰点就说没生效**。

**19 种开关对照表**（最后一列是"怎么用命令核对"，命令都省略了开头的 `adb shell`）：

| 开关 | 按确认键会发生什么 | 需要什么条件 | 怎么核对（adb shell …） |
|---|---|---|---|
| WLAN | 开/关 WiFi | 老系统直接切；新系统可能跳到系统 WiFi 设置页 | `settings get global wifi_on` → `1` 开 / `0` 关 |
| 移动数据 | 开/关数据网络 | 同上，可能需要 mini_shizuku | `settings get global mobile_data` → `1` / `0` |
| 蓝牙 | 开/关蓝牙 | 无 | `settings get global bluetooth_on` → `1` / `0` |
| 飞行模式 | 开/关飞行模式 | 无 | `settings get global airplane_mode_on` → `1` / `0` |
| 手电筒 | 开/关手电筒 | 无 | **命令查不到**，只能看界面 + 闪光灯 |
| 情景模式 | 在「标准响铃 → 震动 → 静音」之间循环 | 无 | `dumpsys audio \| grep -i "ringer mode"` → `RINGER_MODE_NORMAL / VIBRATE / SILENT` |
| 自动旋转 | 开/关屏幕自动旋转 | 无 | `settings get system accelerometer_rotation` → `1` / `0` |
| 一键锁屏 | 锁屏（同【桌面-07】） | 设备管理员 | 点完立刻看 `dumpsys power \| grep -i mWakefulness` → 通常是 `Asleep`（辅助判断） |
| 屏幕亮度 | 在「低 → 中 → 高 → 自动」四档之间循环 | 需要 mini_shizuku | `settings get system screen_brightness` → 低/中/高 = `30 / 150 / 255`；自动档看 `screen_brightness_mode` = `1` |
| 位置信息 | 开/关定位 | 可能需要 mini_shizuku | `settings get secure location_mode` → `3` 开 / `0` 关 |
| 个人热点 | 开/关热点 | 可能需要 mini_shizuku | **命令不可靠**（随 ROM 变），只能看界面；新系统上多半是跳设置页 |
| 省电模式 | 开/关省电模式 | 无 | `settings get global low_power` → `1` / `0`。**开完回待机屏，顶栏电池格会变黄**（见【桌面-20】） |
| 一键冻结 | 把冻结名单里的应用全部冻结 | 需要 mini_shizuku | 见【桌面-15】：`pm list packages -d --user 0` 应该出现这些包 |
| 一键解冻 | 把冻结名单里的应用全部解冻 | 需要 mini_shizuku | 见【桌面-15】：上面那条命令里这些包应该消失 |
| 清理后台 | 清掉后台应用，提示「已清理 N 个后台应用」或「后台已是最新，无须清理」 | 需要 mini_shizuku | 执行前后对比 `ps -A \| grep <包名>`（间接判断，见【桌面-16】） |
| 关机 | **本轮不测**（见【桌面-17】） | 必须 mini_shizuku | — |
| 重启 | 二次确认后重启系统 | 必须 mini_shizuku | 见【桌面-17】：重启前后比 `cat /proc/uptime` |
| 重启到 Recovery | **本轮不测**（见【桌面-17】） | 必须 mini_shizuku | — |
| 重启到 Fastboot | 二次确认后重启到 fastboot | 必须 mini_shizuku | 见【桌面-17】：用 `fastboot devices` 判定 |

**通过标准**：每一行都**按最后一列的命令核对过**、结果与开关动作一致。界面上的图标明暗和圆点只作参考。

**降级行为（不是故障）**：没激活 mini_shizuku 时，有些开关会**跳到系统设置页**让你手动开，而不是直接帮你切。

**我的依据**：`KeydroidxQuickToggleItem`（19 个类型）、`KeydroidxQuickToggleManager`（`toggle()` 与 `isToggleOn()`——注意 `FREEZE / UNFREEZE / CLEAN_BG / LOCK` 和四个电源类的"开状态"恒为 false，所以它们的小圆点不作数）；`docs/5-快捷开关功能设计.md`。

**你要重点看的地方**：附录 C 的 C2（电源类默认不显示）。

#### 【桌面-13】情景模式开关

**应该看到**：每按一次切换一档，并弹出提示，依次是「已切换为震动模式」「已切换为静音模式」「已切换为标准响铃」，然后循环。

**怎么用命令核对**：每切一档，在电脑上跑一次 `adb shell dumpsys audio | Select-String "ringer mode"`，应该依次看到 `RINGER_MODE_VIBRATE` → `RINGER_MODE_SILENT` → `RINGER_MODE_NORMAL`。

**我的依据**：`KeydroidxQuickToggleManager`（Toast 文案）。

#### 【桌面-14】亮度开关

**这条测什么**：屏幕亮度四档循环。

**怎么做**：把高亮移到亮度开关，**连按几次确认键**。

**应该看到**：每按一次切换一档，提示依次是「亮度：低」「亮度：中」「亮度：高」「亮度：自动」，然后循环；屏幕实际亮度跟着变。

**通过标准**：四档轮着来，屏幕亮度真的变化。

**需要什么条件**：mini_shizuku。没激活时会提示「需要 mini_shizuku 才能调节亮度」；已激活但命令下发失败时提示「亮度写入失败」（并跳到系统显示设置）。

**怎么用命令核对**：一边连按切换，一边看 `adb shell settings get system screen_brightness`——「低 / 中 / 高」对应 `30 / 150 / 255`；切到「自动」时看 `adb shell settings get system screen_brightness_mode` = `1`。

**我的依据**：`KeydroidxQuickToggleManager`（三档亮度常量 30 / 150 / 255）。

#### 【桌面-15】一键冻结 / 一键解冻

**这条测什么**：批量冻结、批量解冻，并且要**用命令确认真的冻上了**。

**前置（必须先造名单，不然没得测）**：

1. mini_shizuku 已激活。
2. 在功能表里挑 **2~3 个不重要的应用**，逐个「选项 → 加入冻结列表」（见【功能表-04】）。这一步**只是进名单，不冻结**。
3. **先按一次「一键解冻」**，把起点统一成"全部解冻"。
4. 在电脑上查出这几个应用的**包名**：`adb shell pm list packages | Select-String 关键字`。

**第 1 步 · 记录起点**

`adb shell pm list packages -d --user 0`（列出系统里"当前被禁用"的包）。这一步**不应该**出现你刚加的那几个包。

**第 2 步 · 冻结**

把高亮移到「一键冻结」开关，按确认键。

**应该看到**：提示「已一键冻结 X/Y 个应用」（X = 成功个数，Y = 名单里在本机存在的个数）。**这个开关没有二次确认，按下去直接执行。**

**第 3 步 · 用命令确认（关键）**

- `adb shell pm list packages -d --user 0` → 现在**应该出现**刚才那几个包。
- 想看单个包更准：`adb shell dumpsys package <包名>` → 找 `enabled=` 字段：`enabled=3`（或 `2`）= 已被禁用；`enabled=0 / 1` = 没冻结。
- 如果走的是设备管理员通道，同一段里会有 `hidden=true`，也算冻结成功。

**第 4 步 · 解冻**

把高亮移到「一键解冻」，按确认键。

**应该看到**：提示「已一键解冻 X/Y 个应用」；再跑一次 `pm list packages -d --user 0`，那几个包**应该消失**。

**第 5 步 · 界面确认（辅助）**

回功能表看那几个应用：冻结时图标上会盖一层**冰块效果**，解冻后消失。

**空名单 / 都不存在的情况（也要各测一次）**：

| 情况 | 冻结时的提示 | 解冻时的提示 |
|---|---|---|
| 名单是空的 | 「冻结名单为空，请在功能表中添加」 | 「冻结名单为空」 |
| 名单里 N 个在本机都不存在 | 「冻结名单中的 N 个应用在本机均不存在」 | 同上 |

**通过标准**：`pm list packages -d` 的结果与开关动作**完全对应**（冻结后出现、解冻后消失）；提示里的 X/Y 与实际一致。

**需要什么条件**：mini_shizuku（或 root）。两条通道都不可用时**会静默失败**（提示里的 X 是 0），所以**必须以命令核对为准**。

**⚠️ 别被小圆点骗了**：「一键冻结 / 一键解冻」的小圆点永远是灰的，它不反映状态（见【桌面-12】）。

**我的依据**：`KeydroidxFreezeManager`（冻结 = `am force-stop <包名> ; pm disable-user --user 0 <包名>`，解冻 = `pm enable <包名> ; pm unhide <包名>`；它判断"冻没冻"读的就是系统的 `enabled` 状态）；`KeydroidxQuickToggleManager`（`freezeAll` / `unfreezeAll` 与各提示文案）。

#### 【桌面-16】清理后台

**这条测什么**：一键清理后台应用。

**怎么做**：先随便开几个应用再回桌面，把高亮移到「清理后台」，按确认键。

**应该看到**：提示「已清理 N 个后台应用」；没有可清理的会提示「后台已是最新，无须清理」。

**需要什么条件**：mini_shizuku。

**怎么用命令核对**：清理前 `adb shell pidof <包名>`（或 `adb shell ps -A | Select-String <包名>`）能看到目标进程；按下开关后再查一次，目标进程**应该没了**。注意这只是**间接判断**——有些应用会被系统服务立刻拉起来，"还在"不等于没清理，最终以提示里的数字为准。

**我的依据**：`KeydroidxQuickToggleManager`、`KeydroidxBgManagerHelper`（批量 `am force-stop`）。

#### 【桌面-17】电源类开关（关机 / 重启 / Recovery / Fastboot）

**这条测什么**：电源操作。四个开关**默认不显示**，要先在「桌面设置 → 桌面内容 → 快捷开关」里勾上。

**四个开关共同的二次确认**：按确认键后弹一个框——标题分别是「确认关机」「确认重启」「确认重启到Recovery」「确认重启到Fastboot」，里面两个选项：左边「确认XXX」（选它才执行）、右边「取消」。**不确认不会执行。**

**⚠️ 顺序提醒**：重启类会打断后面的测试，**放在本轮最后测**。

---

**① 关机 —— 本轮不测**

原因：关机后没法用命令自动开机，会卡死整个自动化流程。**这条跳过**，测试报告里注明即可。

---

**② 重启 —— 测，而且要能证明"真的重启了"**

**怎么做**：

1. 重启**前**先记一个数：`adb shell cat /proc/uptime`（输出两个数字，**第一个是"开机到现在多少秒"**）。
2. 按确认键 → 选「确认重启」。
3. 电脑上等它回来：`adb wait-for-device`（设备会断开几十秒，这条命令会一直卡着直到设备重新连上）。
4. 设备回来后再查一次：`adb shell cat /proc/uptime`。

**通过判定**：第 4 步的数字**明显比第 1 步小**（比如从 12345 秒变成 40 秒）= 确实重启了。
如果两次差不多、甚至更大 → **没真的重启**，判不通过。

**辅助判据**：`adb shell getprop sys.boot_completed`（重启过程中读不到或为空，系统起来后变成 `1`）。

**提示文案**：确认后弹「正在重启...」；mini_shizuku 没激活时弹「需要 mini_shizuku 权限才能重启」（且不会执行）。

---

**③ 重启到 Fastboot —— 测，而且能自动拉回来**

**怎么做**：

1. 按确认键 → 选「确认重启到Fastboot」。
2. 电脑上先确认 adb 掉了：`adb devices`（应该看不到设备）。
3. 换 **fastboot 工具**看：`fastboot devices` → **应该能看到设备序列号**，这就证明真的进了 fastboot。
4. 把它拉回系统：`fastboot reboot`。等十几秒，`adb devices` 重新看到设备、`adb shell getprop sys.boot_completed` = `1`，就算回来了。

**通过判定**：`fastboot devices` 能看到设备 = 成功进入 fastboot；`fastboot reboot` 后系统能正常起来 = 全流程可自动完成。

**需要什么条件**：电脑装了 fastboot（Android platform-tools 自带）；手机 mini_shizuku 已激活。

**如果 `fastboot devices` 看不到设备**：多半是 USB 驱动问题，装一下 Android 通用驱动再试；实在不行这条记「跳过（环境不具备）」，不算不通过。

---

**④ 重启到 Recovery —— 本轮不测**

原因：recovery 是整份清单里**唯一一个"进去之后可能失联"的操作**——原厂 recovery 通常没有 adb 通道，一旦进去，电脑这边就完全发不出命令，那句"跳过"本身都得靠人去按电源键才能完成，跟"全自动测试"的前提直接冲突。

而且**没法事先安全验证**：桌面这个开关执行的就是 `reboot recovery`，跟电脑上敲 `adb reboot recovery` 完全一样，想"先试一次看能不能回来"就得先真的进去。

**这条跳过**，报告里注明即可。以后若要单独验证（比如换了带 adb 的第三方 recovery），**人一定要在场**。

---

**别被小圆点骗了**：这四个电源开关的小圆点永远是灰的，不反映状态（原因见【桌面-12】的"小圆点不作数"一节）。

**我的依据**：`KeydroidxQuickToggleManager`（命令分别是 `reboot -p` / `reboot` / `reboot recovery` / `reboot bootloader`，都带 `setprop sys.powerctl` 兜底；只走 mini_shizuku，没有 root 通道、执行后不回读，所以只能靠设备状态判定）；`KeydroidxDesktopFragment`（二次确认弹窗的标题与两个选项）。

#### 【桌面-18】长按按键：只有方向键会"连发"

**这条测什么**：按住一个键不放时会发生什么。这条最容易把"故意设计"当成"按键坏了"。

**怎么做**：在待机屏（或任意页面）**按住不放**：

| 按住的键 | 会发生什么 |
|---|---|
| 方向键（上 / 下 / 左 / 右） | 高亮**连续移动**（连发放行，方便快速翻长列表） |
| 确认键 / 左软键 / 右软键 / 返回键 | **只触发一次**，继续按住不会重复触发（连发被吞掉） |

**通过标准**：方向键连发、其他键不连发。

**千万别当成 bug**：其他键长按"没反应"是**故意防手滑**——刻意吞掉了非方向键的连发，避免长按导致菜单反复弹出、误执行第一项。选项弹窗里同样是这个规则。

**我的依据**：`KeydroidxDesktopActivity` 的 `dispatchKeyEvent`（`getRepeatCount()>0` 过滤，方向键除外）；`KeydroidxOptionsDialog` 同款过滤。

#### 【桌面-19】顶栏点不了（纯展示）

**这条测什么**：确认顶栏所有元素都不响应点击，防止测试时误判成"失灵"。

**怎么做**：待机屏上依次点一下信号格、WiFi 图标、电池、时钟（顶栏），以及大时钟区的时间 / 运营商名 / 日期 / 星期·农历。

**应该看到**：**没有任何反应**——顶栏和大时钟区都没有点击行为，时钟只是自己走字（顶栏每秒、大时钟每分钟）。

**通过标准**：点了没反应 = 正常，不是坏了。

**我的依据**：`StatusBarController`（只读刷新、无点击监听）；`KeydroidxBaseActivity`（顶栏时钟每秒刷新文字）；`KeydroidxDesktopFragment` 的 `clockPanel`（大时钟区无点击监听、分钟级 tick）。

#### 【桌面-20】省电模式开关 + 顶栏电池变黄

**这条测什么**：省电模式要**跨两个地方一起验证**——开关栏的状态，和顶栏电池格的颜色。

**怎么做**：

1. 待机屏，把高亮移到最下面开关栏的「省电模式」，按确认键打开。
2. **按一次 Home 回待机屏**（或切走再切回来），看顶栏的电池格。

**应该看到**：

- **顶栏电池格子变成黄色**（前提是电量 > 10%；如果同时电量 ≤10%，那仍然是红色，见【桌面-02】的规则）。
- 开关栏上这个开关的小圆点变蓝、图标变亮。

**怎么用命令核对**（自动判定的关键）：

| 查什么 | 命令 | 期望 |
|---|---|---|
| 省电模式到底开没开 | `adb shell settings get global low_power` | 开 = `1`、关 = `0` |
| 系统自己怎么认的 | `adb shell dumpsys power \| Select-String mPowerSaveMode` | `mPowerSaveMode=true / false` |

**再按一次关闭**：电池格应该**变回原来的颜色**（绿或红），`low_power` 变回 `0`。

**通过标准**：命令查到的状态与开关动作一致，**并且电池颜色真的跟着变了**（黄 ↔ 原色）——颜色这项只能靠截图对比，命令查不出来。

**需要什么条件**：无（不需要 mini_shizuku）。

**⚠️ 两个容易误判的点**：

1. **电量低于 10% 时系统可能自己就进了省电模式**，这时 `low_power` 本来就是 `1`——测之前先确认电量充足，免得把系统的自动行为算到开关头上。
2. 顶栏是**回到桌面时才重读状态**的，所以切完开关如果颜色没马上变，**按一次 Home** 再看。

**我的依据**：`KeydroidxQuickToggleManager`（切换走 `cmd power set-mode 1|0 ; settings put global low_power 1|0`；`isToggleOn` 用 `PowerManager.isPowerSaveMode()`，异常时回退读 `low_power`）；`KeydroidxBatteryDrawable`（省电模式 → 电池格变黄，完整规则见【桌面-02】）。

#### 【功能表-02】方向键怎么走、怎么翻页

**这条测什么**：宫格导航规则。这条最容易把"正常"误判成"坏了"。

**从哪开始**：功能表。

**应该看到的规律**：

1. 按 `下` → 高亮从第 1 行跳到第 2 行的**同一列**。
2. 在某行**最左边**按 `左` → 跳到**同一行最右边**（在一行里绕圈，不会跑到别的行）。
3. 在某行**最右边**按 `右` → 回到本行最左边。
4. 一直按 `下`，走到本页最后一行后**再按一次 `下`** → 翻到下一页，页码变 `2/N`，高亮落在新页第一行。
5. 在第 1 行按 `上` → 翻回上一页（已在第 1 页时按不动，不报错）。

**通过标准**：左右键只在同一行里绕圈，上下键负责换行和翻页，翻页时右上角数字一定变。

**千万别当成 bug**：左右键"不换行、在一行里绕圈"是故意设计的。

**我的依据**：《AI按键操作手册》第 4.1 节；`KeydroidxMenuFragment` 的方向键处理。

#### 【功能表-05】冻结一个应用、看冰块效果

#### 【功能表-06】换个图标 / 恢复默认图标

**这条测什么**：给单个应用换图标。

**怎么做**：

1. 高亮一个安卓应用 → 左软键「选项」→「更换图标」。
2. 会进入「选择图标包」页 → 选一个图标包 → 进入「选择图标」页 → 在图标网格里挑一个 → 确认。

**我的依据**：`KeydroidxIconPackSettingsFragment`、`KeydroidxIconPickerFragment`、`KeydroidxMenuFragment` 的图标就地刷新逻辑。

**这条测什么**：从功能表卸载应用、跳系统的应用详情页。

**⚠️ 用哪个应用来测（重要，别随手卸）**：**禁止拿系统应用或正在用的应用开刀**。统一用**图标包 APK** 当"牺牲品"——装、卸随意，不影响任何功能：

- APK 在 `<test>\icon\` 下，三个任选：`NokiaIconPack-3D-2007` / `NokiaIconPack-Classic-2008` / `NokiaIconPack-OVI-2009`（都是 `v1.0.0`）。

**第 0 步 · 先把"牺牲品"装上**


第二条应该能看到刚装的包名——**先记下它是哪一个**（下面判定要用）。

**第 1 步 · 卸载**

**应该看到**：跳到**系统的卸载确认页**（不是直接删）。在系统页上按确认键执行卸载。

**第 3 步 · 看应用设置**

**应该看到**：跳到**系统的应用详情页**；按返回键能回功能表，功能表一切正常。

**通过标准**：

- 卸载：跳系统确认页；确认后**包真的从系统消失**（命令查不到）+ 功能表格子消失，两条都对才算过。
- 应用设置：跳到系统应用详情页，返回后功能表正常。

**我的依据**：`KeydroidxMenuFragment`（跳转的是系统 Intent，桌面只负责跳，卸载本身由系统页完成）。

### 3.3 应用程序（JAR / 百宝箱）

> 这是桌面自己管理 J2ME（JAR）应用的地方，**界面标题是「应用程序」**。注意它和「J2ME Loader」那个格子进的自带外壳是两回事。

#### 【应用程序-01】应用程序页长什么样

**从哪开始**：待机屏 → 左软键「功能表」→ 找到**写着「应用程序」的格子** → 按确认键。

**应该看到**：

- 底部中栏标题是「应用程序」，右软键是「退出」。
- **左软键的文字会变**，取决于高亮在哪：
  - 停在**第 1 格「安装」**上 → 左软键**不显示**；
  - 停在**第 2 格「JAR全局设置」**上 → 左软键显示「同步全部」；
  - 停在**第 3 格起的 JAR 应用**上 → 左软键显示「选项」。

**⚠️ 空态判定（重点）**

一个 JAR 都没装时，页面"内容区"没有应用格子——这正常。但**「安装」和「JAR全局设置」这两个格子必须永远在**；连它们都没有、整个页面一片空白，**就是 bug**：

- 代码里这两个格子是**首帧无条件渲染**的（格子总数 = 2 个固定入口 + 已装数量，空列表时也至少有这 2 格），注释明确写着"无缓存也必须展示安装与 JAR 全局设置基础入口"。
- 遇到"整页全空"：**截图 → 记录为 bug → 不要放过去**。"空态正常"指的只是列表区没有 JAR，从来不包括"入口也没了"。

**判 bug 时的排查线索**：

- logcat 里 `Box` 标签应有「首帧同步构建网格完成，应用数：N」——**没这条**说明构建压根没执行；**有这条还全空**说明是渲染层的问题。
- 注意区分两种"看似空"的**正常**情况：首次进入弹**存储权限申请**、工作目录不可用时弹**「无法访问存储」**——这两种是弹窗盖住了页面，不是空白页。

**通过标准**：

1. 空列表时「安装」「JAR全局设置」两格**必须可见、可聚焦、可进入**（确认键分别能打开文件选择器和全局设置）；
2. 左软键文字随高亮位置变化，对得上上面三条；
3. 任何情况下都**不允许出现"连入口都没有"的全空页面**——出现即 bug。

**需要什么条件**：无（空态也是有效状态）。

**我的依据**：`KeydroidxBoxFragment`（首帧无条件 `buildGrid()`、"无缓存也必须展示基础入口"的注释、`totalGridCells = 2 + appItems.size()`、`getSoftLeftText()` / `updateSoftKeys()`、进入即申请存储权限）。

#### 【应用程序-02】装一个 JAR

**怎么做**：把高亮移到第 1 格「安装」→ 按确认键 → 会打开系统的文件选择器 → 选一个 `.jar` 文件。

**应该看到**：选完文件后立刻弹出诺基亚风格的安装弹窗。**这个弹窗会随着安装阶段换内容**：

| 阶段 | 标题 | 中间显示 | 左软键 | 右软键 |
|---|---|---|---|---|
| 正在读取 | 安装 | 正在加载... | 取消 | 不显示 |
| 正在安装 | 安装 | 正在安装... | 取消 | 不显示 |
| 需要你确认 | 见下 | 一句确认说明 | 主操作 | 次操作 |
| 安装完成 | 安装完成 | 安装成功 | 打开 | 完成 |
| 安装失败 | 安装失败 | 错误：<原因> | 不显示 | 确定 |

「需要你确认」这一档按情况分几种：重复安装（左「重新安装」）、版本更新（左「更新」右「取消」）、降级安装（左「仍要安装」右「取消」）、签名不匹配（左「继续安装」右「取消」）、选的不是 JAR（左「选择文件」）。

**关于确认键**：**只有在"需要你确认"那一刻，按确认键才等于按左软键**；其它阶段按确认键没有效果。

**通过标准**：装完回到「应用程序」页，列表里多出这个 JAR。

**需要什么条件**：存储权限（没有权限会提示「没有存储权限，无法运行 JAR 应用」）。

**我的依据**：`KeydroidxBoxFragment` 的安装逻辑、`KeydroidxInstallerDialog`（各状态文案已核对）。

#### 【应用程序-03】把全局设置同步给所有 JAR（含"设置真的同步过去了"验证）

> ⚠️ **这条不能只看弹窗和提示文案**：必须改一个**具体设置值**，同步后进单个 JAR 的设置页核对新值确实生效，最后还原。只看到"已同步 N 个 JAR"不算通过。

**前提**：至少装了 1 个 JAR（本机为「UC浏览器」）；先记住一个**可量化设置**的当前值（本机全局分辨率默认 240×320）。

**怎么做（四步）**：

1. **改值**（改一个和现在不一样的值）
   高亮第 2 格「JAR全局设置」→ 按确认键进入全局配置编辑器 →「屏幕选项 → 分辨率」由 240×320 改成 **360×640** → 返回「应用程序」页。
   - 注：全局编辑器是 J2ME-Loader 原生界面（非诺基亚风格），属正常，见【应用程序-07】。
   - 改完建议先返回确认"全局设置页里已是新值"，再进行下一步。
2. **同步**
   高亮第 2 格「JAR全局设置」→ 按左软键（显示「同步全部」）→ 弹二次确认（大意「同步全局设置：将覆盖所有已装 JAR 的设置，确定？」）→ 确认 → 提示「已同步 N 个 JAR」。
3. **核对同步结果（关键步骤，本用例的重点）**
   高亮任一个 JAR → 左软键「选项」→「设置」→ 进到同一个「屏幕选项 → 分辨率」，**确认显示的是刚改的新值 360×640**（而不是旧值 240×320）。
   - 这是"设置真的同步过去了"的唯一证据；跳过这步等于没测。
4. **还原（必做，不能留后遗症）**
   回到「JAR全局设置」把分辨率**改回 240×320** → 再按「同步全部」→ 再进那个 JAR 的设置页，确认已回到 240×320；全局设置页也确认回到原值。

**应该看到**：

- 二次确认弹窗；确认后提示「已同步 N 个 JAR」（没有可同步的 JAR 时提示「无可同步的 JAR」）。
- 第 3 步：单 JAR 设置页里读到的是**新值**（360×640）。
- 第 4 步：还原后单 JAR 设置页与全局设置页都回到**原值**（240×320）。

**通过标准**：

1. 有二次确认，提示文案正确；
2. **单 JAR 设置页能读到同步后的新值**——证明设置真的落到了每个 JAR，而不只是弹了个框；
3. **还原后单 JAR 与全局设置均回到原值**，设备不留后遗症。

**需要什么条件**：已装 ≥1 个 JAR。（分辨率只是示例值，用别的可量化设置——屏幕方向、缩放类型等——同样可测。）

**我的依据**：`KeydroidxBoxFragment` 的 `showSyncAllDialog()`。

#### 【应用程序-04】启动一个 JAR

**怎么做**：高亮任意一个 JAR → 按确认键。

**应该看到**：进入 J2ME 运行界面（游戏/应用开始跑）。

**通过标准**：JAR 能启动。

**⚠️ 注意**：JAR 运行在独立进程里，**它崩溃不会拖垮桌面**，桌面回到待机屏是正常表现。

**我的依据**：`KeydroidxJarLauncher`。

#### 【应用程序-05】改一个 JAR 的设置

**怎么做**：高亮一个 JAR → 左软键「选项」→「设置」。

**应该看到**：进入该 JAR 的配置页（屏幕方向、按键映射等，属于 J2ME-Loader 原有能力）。

**通过标准**：能进设置页，改完能返回。

**我的依据**：`KeydroidxBoxFragment`（调用 `Config.startApp(..., true)`）。

#### 【应用程序-06】卸载一个 JAR（弹窗按键规则，重点）

**这条测什么**：诺基亚风格确认弹窗的按键规则。这里有个反直觉点。

**前提**：至少装了一个 JAR。

**怎么做**：高亮一个 JAR → 左软键「选项」→ 选「卸载」。

**应该看到**：弹出一个确认小窗，标题「卸载」，内容「是否卸载「<应用名>」？」。底部两个软键：**左边「卸载」、右边「取消」**。

**关键规则（逐个试一遍）**：

| 你按的 | 会怎样 |
|---|---|
| **确认键** | **什么都不发生**，弹窗也不关（故意防手滑） |
| **左软键** | 真的卸载，弹窗消失 |
| **右软键** | 取消，弹窗消失 |
| **返回键** | 等同取消 |
| **左右方向键** | 没反应（弹窗里方向键左右无效） |

**通过标准**：确认键确实"没反应"；左软键真的删掉；右软键取消不删。

**补充**：卸载**没有额外的成功提示**，列表里那个 JAR 消失了就代表成功了。

**我的依据**：`KeydroidxUninstallDialog` + `dialog_keydroidx_uninstall.xml`（已核对：左软键=卸载、右软键=取消）。

**你要重点看的地方**：确认键"没反应"这个设计你还要不要；想改成"确认键=取消"就得改代码。

#### 【应用程序-07】「JAR全局设置」格子

**这条测什么**：第 2 格「JAR全局设置」按确认键进去是什么。

**怎么做**：把高亮移到第 2 格「JAR全局设置」→ 按确认键。

**应该看到**：进入 J2ME-Loader 的配置编辑器（屏幕方向、按键映射、滤镜之类，**和单个 JAR 的设置页是同一个界面**），只不过作用对象是「全局」——在这里改的值，是之后每个 JAR 的默认设置。

**通过标准**：能进、能改、能返回，不闪退。

**说明**：这个编辑器是 J2ME-Loader 原有能力，界面不是桌面风格，属正常。另外，桌面自己的 7 个核心按键绑定会作为默认值同步进全局配置（你手动改过映射的应用除外）。

**我的依据**：`KeydroidxBoxFragment`（确认键 → `KeydroidxGlobalProfile.openGlobalSettings`）；`KeydroidxGlobalProfile`（自动同步桌面按键绑定）。

#### 【应用程序-08】JAR 挂机后继续在后台运行

**这条测什么**：J2ME 应用运行时回到桌面，JAR 会不会被杀掉。

**怎么做**：

1. 从「应用程序」页启动一个 JAR，等它跑起来。
2. 按挂机键（或在 JAR 界面按 Home）回到待机屏。
3. 拉下系统通知栏看一眼，再点那条通知。

**应该看到**：

- 通知栏出现一条常驻通知：**标题是 JAR 的名字**，内容「正在后台运行」（通知渠道叫「JAR 后台运行」）。
- 点这条通知 → 回到那个 JAR，**从刚才的状态接着跑**（不是冷启动重来）。
- 回到 JAR 界面后，这条通知自动消失。

**通过标准**：回桌面后 JAR 不被杀、常驻通知在、点通知能续跑。

**需要什么条件**：较新系统（Android 13+）需要通知权限；没授权时**降级成"没有通知"，但 JAR 仍然在后台跑**——不是崩溃，别误判。

**我的依据**：`KeydroidxMidletKeepAliveService`（`MicroActivity.onStop` 启动 / `onResume` 停止；WakeLock + WifiLock；保活降级逻辑）。

#### 【设置-03】「按键与操作」里有什么

#### 【设置-按键-01】改按键绑定（含冲突处理）

**怎么做**：桌面设置 →「按键与操作」→「按键绑定」。

**应该看到**：左软键「选择」、右软键「返回」。列表 **9 行**，分别是：上、下、左、右、确认、左软键、右软键、锁屏、拨号键。

**怎么做**：高亮「确认」这一行 → 按确认键。

**应该看到**：进入"录制"状态（提示你按下要绑定的键）。这时按下手机的某个物理键。

**应该看到**：

- 进入录制时，屏幕上先出现提示「正在录制: <动作名> — 请按目标键（点此处取消）」，并有一个约 0.8 秒的防抖时间（这段时间内按下的键不算数）。
- 如果这个键**没被占用**：绑定成功，那一行右边显示新键名。
- 如果这个键**已经被别的动作占用**：屏幕下方出现一条提示「按键冲突，请触摸下方按钮选择」，并显示是哪个动作占用了它（格式是「占用的动作名 → 键名」）；下面有两个按钮，**左边「取消」、右边「覆盖」**。

**通过标准**：能绑定；冲突时有提示；选「覆盖」真的抢过来，选「取消」保持原样。

**⚠️ 注意**：要绑的键请**单独按一下**，不要连按（连按会被防抖吃掉）。

**⚠️ 改动即还原（重要，必须遵守）**：

- **只想验证"录制流程能走通"** → 可以**录回同一个键**（比如「上」再按一次「上」）：配置不会变，最省事。**但这只证明流程能跑，证明不了"改绑真的生效"。**
- **要验证"改绑真的生效"** → 必须绑到**另一个键**，然后：① 退出设置页，**实际按一下新键**，确认触发的动作确实变了；② 回绑定页确认那一行右边显示的是**新键名**。
- **测完必须把原键录回去**：重新进入该行录制态，按回原按键（例如「上」的原值是 `KEYCODE_DPAD_UP`），确认那一行右边恢复原键名。
- **还原后双重复核**：① 绑定页显示的键名与原值一致；② `shared_prefs/nokia_key_bindings.xml` 里对应的值也是原值（如 `up=19`）——**在设备上的命令**：`adb shell run-as io.github.cctyl.nokia.debug cat shared_prefs/nokia_key_bindings.xml`。
- **别忘了全局同步**：改绑成功会自动同步进 JAR 全局配置（见【补充-35】），所以**录回原键后要再确认同步已恢复**（对单个 JAR 核对键位，参见【应用程序-03】的四步核对法）。
- **底线**：任何按键绑定都不允许"测完留着"，尤其别把「上/下/确认/左右软键」改成非常规键——下一轮测试和用户日常使用都会直接受影响。

#### 【设置-按键-02】录制态下按返回键会发生什么（重点）

**这条测什么**：按键录制状态下，返回键到底算"取消"还是算"要绑定的键"。**这里和直觉相反，专门测它。**

**怎么做**：进「按键绑定」→ 高亮任意一行 → 按确认键进入录制 → **按一下返回键**。

**应该看到**：返回键被**录成了这个动作的绑定键**（那一行右边显示返回键的名字），并没有"取消录制"。想取消录制，只能**触摸点屏幕上那条提示**（「点此处取消」）。

**通过标准**：返回键在录制态 = 被绑定，不是取消。

**反直觉点（要重点看）**：这意味着**纯按键用户在录制态没有任何"取消"手段**，只能靠触摸。如果这不可接受，需要改代码（比如允许录制态用返回键取消）。见附录 C 的 C9、C10。

**我的依据**：`KeydroidxDesktopActivity` 的 `dispatchKeyEvent`（录制态把任意键码直接喂给 `onKeyRecorded`，**含返回键**）；`KeydroidxKeyBindFragment` 的取消只挂在触摸点击上。

#### 【最近任务-01】查看和管理后台任务

**怎么进**：待机屏按**拨号键**（就是平时打电话那个绿色键）；或者点桌面上的「后台管理」组件。

**应该看到**：底部中栏「最近任务」，左软键「选项」（空态时不显示）、右软键「退出」。内容是 **2 列卡片**，每张卡片是一个后台应用。顶部有一个模式徽标（**「实时」** 或 **「未激活」**）和一行说明：「确认键回到应用 · 5 清理选中 · 0 清理全部 / 拨号键呼出本页（桌面按下即进入）」。

**怎么做**：高亮一张卡片 → 按确认键。

**应该看到**：切回那个应用。

- **正在读取**：显示「正在读取最近任务…」，等一会儿就好。
- **mini_shizuku 没激活**：显示「未激活 mini_shizuku」，下面有一行说明，还有一个「去激活 mini_shizuku」按钮。

**通过标准**：能列出后台应用、确认键能切回去；空态显示对应提示而不是空白崩掉。

**怎么造数据、怎么判对错**：见【桌面-08】的第 0~2 步——先用 `scripts\recents.ps1 -Seed "包名1,包名2"` 打开几个**已知的应用**，再用 `.\recents.ps1 -List` 读出**系统记录**当标准答案；本页卡片应该和它一致（最近打开的在最前）。不这么做的话，你没法判断"列表里该有几个、该有谁"。

**需要什么条件**：较新的系统 + mini_shizuku（未激活时功能受限，属于预期）。

**我的依据**：`KeydroidxRecentTasksFragment`。

#### 【最近任务-02】最近任务的选项菜单

**怎么做**：最近任务页 → 左软键「选项」。

**应该看到**：弹出菜单，包含：打开应用 / 保护此应用 / 刷新列表 / 清理此任务（会有二次确认）/ 清理全部任务 / 激活 mini_shizuku。**「保护此应用」的文案随状态变**：已保护的卡片上这一项显示「取消保护」（图标换成开锁），卡片预览区右上角会有绿色盾牌角标。保护名单的完整测法见【桌面-08】第 5 步。

**「清理此任务」的确认框按键规则（容易按错，重点）**：安全选项放在左边——
**左软键 = 取消，右软键 = 清理**；而且**确认键等同左软键 = 取消**。
也就是说：误按确认键只会取消，不会删掉；**想真清理必须按右软键**。

**通过标准**：菜单项完整；「清理此任务」有二次确认，且确认框里确认键只取消、右软键才删。

**我的依据**：`KeydroidxRecentTasksFragment`（`confirmClearTask`：positive=取消、negative=清理，确认键与左软键等效）。

#### 【最近任务-03】保护一个应用不被批量清理

**这条测什么**：「保护此应用」到底挡什么、不挡什么。

**怎么做**：最近任务页 → 高亮一张卡片 → 左软键「选项」→「保护此应用」。

**应该看到**：提示「已保护「XX」」；这张卡片的预览区**右上角多一个绿色盾牌**；再按「选项」，这一项变成「取消保护」。

**保护的范围（重点）**：只挡批量清理（数字键 0 / 选项「清理全部任务」），**不挡**手动单清（「清理此任务」/ 数字键 5）——完整论证和实测步骤见【桌面-08】第 5 步。

**通过标准**：盾牌能加能取消；批量清理跳过被保护应用，手动单清照清。

**说明**：保护名单**重启不丢**（存在设置里）。

**我的依据**：`KeydroidxRecentTasksFragment`（`toggleProtect`、盾牌角标、保护语义注释）。

#### 【最近任务-04】数字键 5 / 0 的快捷清理

**这条测什么**：最近任务页的两个数字键快捷键。

**怎么做**：最近任务页，直接按数字键 **5**；再按数字键 **0**。

**应该看到**：

- 按 **5** = 清理当前高亮那一个任务，**没有二次确认**。
- 按 **0** = 一键清理所有**没被保护**的任务，**没有二次确认**。

**通过标准**：两个键都能清；按 0 时被保护的应用不被清。

**⚠️ 注意**：这两个键都没有二次确认，测之前先确认高亮位置。

**我的依据**：`KeydroidxRecentTasksFragment`（数字键 5 / 0 处理，均无二次确认）。

### 5.2 系统级行为

#### 【挂机键-01】挂机键（红键）的完整行为

**这条测什么**：把电源键当"挂机键/红键"用时，各种情况下的行为。**这是本桌面最核心的特性之一。**

**⚠️ 最重要的前提**：**必须用手按物理挂机键**。用 adb 发的模拟按键会绕过这套机制，测不出来。

**准备工作**：

1. 先激活 mini_shizuku（见 4.2「高级设置」组）。
2. 进「高级设置 → 电源键拦截设置」→ 选「方案1：grab+回放」或「方案2：纯消费」（选到提示「拦截已启动」为止）。
3. 如果没开拦截，挂机键就是系统原来的行为（休眠/关机菜单），下面的表都不适用。

**8 个场景的完整行为表**（"按 1/2/3"指连续按第 1、2、3 次）：

| # | 起点 | 第 1 次按 | 第 2 次按 | 第 3 次按 |
|---|---|---|---|---|
| 1 | 亮屏 + 在别的应用里（非桌面） | 回到待机屏（**屏幕仍然亮着**） | 锁屏（熄屏） | 亮屏，显示锁屏界面；解锁后是待机屏 |
| 2 | 息屏 + 在别的应用里 | 亮屏，显示锁屏界面；解锁后回到**原来那个应用** | 回到待机屏 | 锁屏（熄屏） |
| 3 | 亮屏 + 待机屏 | 锁屏（熄屏） | 亮屏，显示锁屏界面；解锁后是待机屏 | 锁屏（熄屏） |
| 4 | 息屏 + 待机屏 | 亮屏，显示锁屏界面；解锁后是待机屏 | 锁屏（熄屏） | 亮屏，显示锁屏界面；解锁后是待机屏 |
| 5 | 亮屏 + 桌面里的小页面（功能表/设置/应用程序） | 回待机屏（**不锁屏，屏幕还亮着**） | 锁屏（熄屏） | 亮屏，显示锁屏界面；解锁后是待机屏 |
| 6 | 息屏 + 桌面里的小页面 | 亮屏，显示锁屏界面；解锁后回到**原来那个小页面** | 回到待机屏 | 锁屏（熄屏） |
| 7 | 亮屏 + 锁屏界面 | 熄屏 | 亮屏，显示锁屏界面；解锁后是原本的界面 | 回到待机屏 |
| 8 | 息屏 + 锁屏界面 | 亮屏，显示锁屏界面；解锁后是原本的界面 | 回到待机屏 | 锁屏（熄屏） |

**记三条规律就够了**：

1. **回到桌面不会熄屏**（只在"亮着屏、又不在待机屏"时触发）。
2. **锁屏一定同时熄屏**，而且只在"亮着屏、且正停在待机屏"时才锁。
3. **黑屏时按第一下，永远是"点亮 + 显示锁屏界面"**，不会直接进桌面；解锁后回到你黑屏前看的东西。

**通过标准**：每按一下都产生新状态，下一次按按新状态算，和上表一致。

**不做休眠/关机的例外**：**长按**挂机键约 1 秒，会弹出系统的关机菜单（这是保留的系统行为）。

**我的依据**：《挂机键行为定义》第 3 节矩阵（8 场景 × 连按 3 次，用户逐条确认过）。

#### 【挂机键-02】确认"没开拦截"时是系统行为

**怎么做**：把「电源键拦截设置」改成「关闭拦截」，然后按一下挂机键。

**应该看到**：恢复系统原来的行为（按一下休眠/熄屏，长按弹关机菜单）。

**通过标准**：关掉拦截后，挂机键不再"回桌面"，而是系统原生行为。

**我的依据**：`KeydroidxPowerInterceptFragment` 的「关闭拦截」项。

#### 【拨号键-01】在待机屏按拨号键打开最近任务

**怎么做**：站在待机屏，按**拨号键**（平时打电话那个键）。

**应该看到**：打开「最近任务」页（用例见【最近任务-01】）。

**通过标准**：一下就进最近任务；按右软键「退出」能回待机屏。

**我的依据**：`KeydroidxDesktopActivity` 的按键分发。

#### 【锁屏-01】桌面上的锁屏入口

见【桌面-07】。三种触发方式都一样：桌面「锁屏」组件 / 快捷开关栏的「一键锁屏」/ 挂机键在待机屏按一下。

#### 【冻结-01】冻结与解冻

见【功能表-05】（单个应用冻结）和【桌面-15】（一键批量冻结/解冻）。要点：

- 冻结真的生效后，功能表图标上会有**冰块**效果；
- 点冻结的应用会**先解冻再启动**；
- 冻结需要 mini_shizuku 或 root。

#### 【冻结-02】解冻启动时的权限自愈

**这条测什么**：解冻一个应用后点它，如果系统里已经解析不到它的启动入口，会发生什么。

**怎么做**（较难复现，可选测）：把一个卸载重装过、或包名变过的应用加进冻结名单并冻结，再解冻、然后点它。

**应该看到**：解冻后解析启动入口失败时，应用会**自动弹一次"应用列表权限"申请**（说明文案大意：需要应用列表权限以定位并启动应用）。授权成功后**自动重试启动**这个应用，不需要你再点一次；如果拒绝，提示「缺少权限，无法启动应用」。

**通过标准**：授权后自动续上启动；拒绝有明确提示，不闪退。

**我的依据**：`KeydroidxFreezeManager` 的 `handleLaunchFailurePermissionRepair()`。

#### 【返回键-01】返回键在各处都是"回上一层"

**这条测什么**：返回键的统一行为，防止测试时误判。

**怎么做**：待机屏 → 右软键进「桌面设置」→ 进「外观与显示」→ 进「字体大小」弹窗 → 按返回键；一路按回到待机屏；最后在待机屏再按一次返回键。

**应该看到**：

- 每按一次返回键 = 退回上一层（有弹窗先关弹窗，再页面出栈），效果和按右软键「返回 / 关闭」一样。
- 回到待机屏（最底层）后，再按返回键**不会退出应用**（本应用就是系统桌面，没有"上一层"可退；表现可能是无变化，不是崩溃）。

**通过标准**：逐层回退、不跳层、不闪退；最底层按返回不退出。

**千万别当成 bug**：设为默认桌面后，在待机屏按返回键"没反应"是正常的。

**我的依据**：`KeydroidxDesktopActivity`（BACK 分发、`exitCurrent()` 出栈、`finish()` 被覆写成出栈而不是退出）；各页面 `onBack()` 统一走 `exitCurrent()`。

### 5.3 开机时自动发生的事

> 这一节全是"你没主动操作、但应用自己会做"的动作。测试时最容易把它们当成"弹窗 bug"。
> 共同前提：应用已完成首启向导（否则先走【启动-01】）。

#### 【启动-01】第一次启动：自动弹「按键向导」，然后连环三件事

**这条测什么**：全新安装（或清过数据）后第一次打开应用，会自动带你走初始化流程。

**前提**：全新安装 / 清过数据。已绑过键的老安装不会弹，可直接跳过本条。

**从哪开始**：装好应用后，第一次打开它。

**应该看到，按顺序**：

1. 弹「应用向导」开头页，二选一：左软键「绑定」、右软键「触屏模式」。
2. 选「绑定」→ 逐个提示「请按下『上』键」「请按下『下』键」……共 9 项（顺序同按键绑定页）。录制期间底部不显示任何软键；屏幕上有「跳过此项」触摸按钮。
3. 9 项录完 → 结束页，左软键「完成」。
4. 按「完成」回桌面后，弹「设为默认桌面？」——选「设置默认桌面」会跳系统的默认桌面选择页；选「稍后再说」、或直接按返回键关掉，都会继续下一步。
5. 如果核心权限有缺失 → 自动跳到「系统权限自检」页引导授权；不缺就直接停在待机屏。

**通过标准**：5 步按顺序走完，最终停在待机屏。

**千万别当成 bug**：结束页底部右软键那一栏是空的（不显示文字），但按右软键或返回键同样算「完成」。

**我的依据**：`KeydroidxDesktopActivity`（`!isWizardDone()` 时加载向导）；`KeydroidxKeyBindWizardFragment`（三态 + 结束后的默认桌面询问与权限自检跳转）。

#### 【启动-02】每次进桌面：核心权限自检

**这条测什么**：不是首次启动时，应用也会自己检查核心权限齐不齐。

**怎么做**：去系统设置把某个核心权限收回（比如「通知使用权」），然后彻底杀掉应用、重新进桌面。

**应该看到**：弹一个**底部弹出的权限引导框**——标题「**系统权限申请**」，正文是「检测到部分系统权限缺失，桌面需要电话状态、应用列表、通知及通知使用权权限，以显示信号、展示和启动应用、并常驻通知」，软键**左「授权」、右「取消」**（按返回键同样能关掉，效果等同取消）。允许后相关功能恢复。

**通过标准**：缺权限才弹、只引导一次；什么都不缺时不弹。

**说明**：**一次启动里只弹一次**。本次拒绝了，本次不再打扰；下次启动仍缺才会再弹。

**我的依据**：`KeydroidxDesktopActivity` 的 `checkCorePermissionsOnStartup()`。

#### 【启动-03】发现新版本：进桌面后弹更新提醒

**这条测什么**：自动检查更新发现新版本后的提醒方式。

**前提**：「自动检查更新」开着（默认开），且 GitHub 上确实有更新的版本。没有新版本时本条直接跳过。

**应该看到**：进入应用约 **1.5 秒**（上次检查遗留的新版本）或约 **15 秒**（本次启动刚检查到）后，弹一个复古风格的确认框。

**软键行为**（代码注释已核对：LSK=更新 / RSK=忽略此版本 / BACK=下次再提醒——"下次提醒"是返回键，不是第三个软键）：

| 你按的 | 会怎样 |
|---|---|
| 左软键「更新」 | 打开浏览器，跳到 GitHub 发布页 |
| 右软键「忽略此版本」 | 关掉，并且以后不再提醒这个版本 |
| 返回键 | 关掉，**下次进应用再提醒** |

**通过标准**：三个软键行为如上；关掉之后**本次启动内不重复弹**。

**我的依据**：`KeydroidxDesktopActivity` 的 `scheduleUpdateReminderDialog()`（1.5s / 15s 两次尝试、会话内只弹一次）；弹窗实现在 core 模块 `KeydroidxAutoUpdateChecker`。

#### 【启动-04】mini_shizuku 开机自恢复

**这条测什么**：mini_shizuku 服务端在手机重启后会消失，应用会尝试自动把它找回来。

**怎么做**：先激活 mini_shizuku → **重启手机** → 等进桌面约 3 秒观察。

**应该看到（按激活方式不同）**：

- **root 模式**：自动执行一次 root 激活，手机弹一次 su 授权框（Magisk 之类），允许后服务恢复在线——不需要你手动去设置里点。
- **adb 模式**：弹一条 Toast 提醒你服务没了、要连电脑重新激活（以前成功激活过才提醒；从没激活过的不打扰）。

**通过标准**：root 机能自动恢复；adb 模式有提醒；同一次开机内只自动尝试一次，不反复弹授权框。

**我的依据**：`KeydroidxShizukuBootRecovery`（延迟 3 秒、锁屏时等解锁、单次守卫）。

#### 【启动-05】保活服务开机自启

**这条测什么**：开着「保活服务」时，每次进桌面都会自动把常驻服务拉起来。

**怎么做**：确认「桌面设置 → 系统与权限 → 保活服务」是开启 → 杀干净应用重新进 → 拉下系统通知栏看。

**应该看到**：通知栏有一条常驻通知，标题「原键桌面」、内容「正在运行」。关掉保活开关再进桌面，这条通知不再出现。

**通过标准**：通知的有无与开关状态一致。

**我的依据**：`KeydroidxDesktopActivity.onCreate`（按设置决定是否启动服务）；`KeydroidxDesktopKeepAliveService`。

### 5.4 触屏操作

> 这个桌面是"按键优先"设计的，但触屏也能用。**按键机（或没有触屏的机器）跳过本节**（含【触屏-01~04】；本节用例会开启「触屏模式」，测完请关回去）。

#### 【触屏-01】底部三栏点一下 = 三个软键

**这条测什么**：底部「功能表 / 桌面设置」那一排可以直接点。

**怎么做**：待机屏上直接点左下角「功能表」、点中间标题、点右下角「桌面设置」。

**应该看到**：分别等同按了左软键、确认键、右软键——点「功能表」进功能表，点「桌面设置」进桌面设置。点下去时那一格会闪一下（和按键一样的反馈）。

**通过标准**：三个格子都能点，行为与对应软键一致。

**我的依据**：`KeydroidxDesktopActivity` 的 `bindBottomBarTouch()`。

#### 【触屏-02】列表行 / 图标点一下 = 高亮 + 确认

**这条测什么**：各页面的行、格子都能直接点，不用先挪高亮。

**怎么做（挑几个试）**：

1. 桌面设置里点某一行 → 高亮跳过去并触发（等同确认键）。
2. 功能表里点一个应用格子 → 直接启动。
3. 待机屏点一个快捷开关 → 直接切换。
4. 待机屏点通知条 → 进通知中心。

**通过标准**：点击效果 = 把高亮移过去按确认键。

**我的依据**：各页面的行 / 格子点击监听（`KeydroidxSettingsGroupFragment`、`KeydroidxDesktopFragment` 的 `setupWidgetRowClick()` 等）。

#### 【触屏-03】功能表滑动翻页

**这条测什么**：功能表里用手指滑动也能翻页（清单其余部分只用按键，这条是触屏专属）。

**怎么做**：在功能表界面（宫格上或空白处）手指**上滑或左滑**。

**应该看到**：翻到下一页（右上角页码变）；**下滑或右滑**翻回上一页。位移约 24dp 以上、或快速轻扫，才判定为翻页；只是点一下不会误翻。

**通过标准**：四个方向翻页方向正确；轻点图标仍然是启动应用，不会误翻页。

**我的依据**：`KeydroidxMenuFragment` 的 `initSwipeListener()`（阈值 24dp / 速度 0.35 px·ms⁻¹）。

#### 【触屏-04】触屏模式（虚拟键盘整套）

**这条测什么**：开了「触屏模式」之后，屏幕底部出现一套虚拟功能机键盘，桌面整体变成"纯触屏"用法。

**前提**：先进「桌面设置 → 按键与操作 → 触屏模式」打开（首启向导开头页选「触屏模式」也行）。

**应该看到**：

1. 屏幕底部出现虚拟键盘：中间是**导航轮**（圆盘，四向 + 中间确认），两侧是**左软键、右软键**，往上是**拨号键、挂机键（同时当 Home 用）**，最下面是 **3×4 九宫格数字键**（`*` 键绑了一键锁屏，`#` 是 # 键）。
2. 桌面主窗口自动让出下半屏给键盘；系统的底部三大按键（菜单 / Home / 返回）被隐藏。
3. 按虚拟键盘上的键 ≈ 按真物理键：有点击音和震动反馈，事件发给当前界面（比如在虚拟键盘上按左软键 = 真左软键）。
4. 弹窗会贴在虚拟键盘上沿，不会被键盘挡住。
5. 导航轮可以用手指转着滑，连续发方向键。

**通过标准**：键盘出现；按键有反馈且真能控制系统；弹窗不被挡；系统三大键隐藏。

**我的依据**：`KeydroidxTouchWindowController`、`KeydroidxVirtualKeypadView`、`KeydroidxNaviWheelView`；设计文档 `docs/触屏模式虚拟键盘双窗口解耦架构与设计文档.md`。

### 6.1 JAR 运行时的操作（正文整块没写）

> 正文只写了"怎么把 JAR 装起来、怎么启动"，但 **JAR 跑起来之后按什么键、会发生什么** 一条都没有。这是最大的一块缺口。

#### 【补充-01】JAR 里按红键 = 一键挂机回桌面

**这条测什么**：J2ME 应用正在跑的时候按红键（挂机键），是不是像真功能机一样"直接挂机回桌面"。

**从哪开始**：从「应用程序」页启动一个 JAR，等它跑起来（能看到游戏/应用画面）。

**怎么做**：按一下**红键**（挂机键）。

**应该看到**：

- **不弹任何菜单**，直接回到待机屏。
- JAR 没有被杀掉，还在后台跑：通知栏出现一条常驻通知，标题是 JAR 的名字、内容「正在后台运行」。
- 点这条通知 → 回到 JAR，**从刚才的画面接着跑**。

**通过标准**：一键回桌面 + 通知在 + 点通知能续跑。

**我的依据**：`MicroActivity` 里红键分支（抬起时执行"后台运行并回桌面"）；`KeydroidxMidletKeepAliveService`。

#### 【补充-02】JAR 里按绿键 = 挂机三菜单（继续 / 退出 / 后台运行）

**这条测什么**：JAR 里按绿键弹出的"老三样"菜单，以及这个菜单自己的按键规则。

**从哪开始**：一个正在运行的 JAR。

**怎么做**：按一下**绿键**（拨号键）。

**应该看到**：弹出「继续 / 退出 / 后台运行」三项菜单。

**菜单里的按键规则**：与通用选项弹窗完全一致（确认/左软键=执行，返回/右软键/挂机键=关闭，上下到头循环，左右无效，不连发）——逐键验证见【补充-14】，本条只验证"关菜单 = 继续跑"这个语义。

**三项分别的效果**：

- **继续**：关掉菜单，JAR 照跑。
- **退出**：先退回桌面（不等 JAR 自己画退出画面），然后在后台销毁——下次进这个 JAR 是重新冷启动。
- **后台运行**：回桌面，通知栏出现常驻通知（同【补充-01】）。

**通过标准**：三项行为如上；返回/右软键/挂机键都只是关菜单。

**我的依据**：`MicroActivity` 的挂机三菜单（复用通用选项弹窗）；`KeydroidxOptionsDialog` 的按键规则。

#### 【补充-03】JAR 里"文本类"界面的软键（TextBox / 表单 / 列表）

**这条测什么**：JAR 内部那些带软键栏的界面（比如登录框、设置列表），左右软键归谁。

**怎么做**：打开一个带软键栏的 JAR 界面（没有这类界面的 JAR 可跳过本条）。

**应该看到**：

- **左软键** = 打开这个界面自己的"操作 / 菜单"。
- **右软键** = 清除 / 返回。
- 方向键、确认键 = 在菜单里移动和执行。

**Canvas 游戏画面**：菜单键透传给游戏自己处理，桌面不拦。

**我的依据**：`MicroActivity` 的 Screen 模式按键路由（DOWN 记录、UP 执行）。

#### 【补充-04】把挂机的 JAR 从后台清掉

**这条测什么**：挂机在后台的 JAR，怎么从最近任务里干净地清掉。

**从哪开始**：先按【补充-01】挂机一个 JAR，然后回桌面按**拨号键**进最近任务。

**应该看到**：挂机的那个 JAR **固定排在最上面**。

**怎么做**：高亮它 → 左软键「选项」→「清理此任务」（或直接按数字键 **5**）。

**应该看到**：JAR 被"优雅退出"（不是被系统强杀），常驻通知消失；回待机屏看「后台管理」组件，数字减 1。

**通过标准**：JAR 真退出、通知消失、桌面计数跟着变。

**我的依据**：`KeydroidxMidletControlReceiver`（显式广播 → 优雅销毁）；`KeydroidxRecentTasksFragment`（挂机 JAR 置顶）。

### 6.2 从文件管理器装 JAR

#### 【补充-05】在系统文件管理器里点开 .jar / .jad 文件

**这条测什么**：不经过桌面，直接从文件管理器打开 JAR 文件，是否走本应用的安装流程。

**怎么做**：用系统文件管理器（或 adb push 一个 jar 到 /sdcard 后用文件管理器点开）点一个 `.jar` 或 `.jad` 文件，选"用本应用打开"（如果系统问的话）。

**应该看到**：直接进入安装流程（和「应用程序 → 安装 → 选文件」一模一样），装完出现在「应用程序」页列表里。

**通过标准**：能装、不闪退、装完列表里有。

**我的依据**：`AndroidManifest.xml` 里 J2ME 入口的"打开文件"过滤器（.jar/.jad/.kjx）。

**需要什么条件**：有一个带文件管理器的系统（或能访问存储的文件 App）。

### 6.3 功能表的实时行为

#### 【补充-06】功能表开着的时候装 / 卸应用

**这条测什么**：应用列表是不是实时跟随系统变化（不用重启桌面）。

**怎么做**：停在功能表页面，用 adb 装一个新应用（或卸掉一个），等 1～2 秒看列表。

**应该看到**：

- 列表**自己**多出 / 少掉这个应用，不用退出重进。
- 尽量保持你当时的页码和高亮位置。
- 如果卸载后总页数变少、当前页变空了，焦点收敛到新的最后一页（不白屏、不闪退）。

**通过标准**：列表实时更新；页码/焦点合理；不崩。

**我的依据**：`KeydroidxMenuFragment` 的"包装载/卸载/替换"广播监听 + 越界收敛逻辑。

#### 【补充-07】三个特殊格上按「选项」= 直接进入

**这条测什么**：防止在特殊格上按选项键"没反应"被误判成坏了。

**怎么做**：功能表里高亮「应用程序」「J2ME Loader」「通知中心」这三个格中的任意一个，按左软键「选项」。

**应该看到**：**不弹菜单**，直接进入对应页面——和按确认键完全一样。

**通过标准**：三个格都直接进得去。

**我的依据**：`KeydroidxMenuFragment.onSoftLeft()`（只对普通安卓应用弹选项菜单）。

#### 【补充-08】有菜单键的机器：菜单键 = 左软键

**这条测什么**：没有独立软键的机器，用菜单键代替"左软键"。

**怎么做**：任意页面按**菜单键**（不是屏幕上的软键栏，是物理菜单键）。

**应该看到**：效果和左软键一样——待机屏进功能表、功能表弹「选项」、设置页=「选择」。

**通过标准**：菜单键处处等同左软键。

**注意**：这是"没给菜单键单独绑定时"的兜底行为；你在「按键绑定」里也可以主动把菜单键绑成任意动作。

**我的依据**：`KeydroidxKeyBinding` 的菜单键兜底分支。

### 6.4 按键与系统行为补充

#### 【补充-09】没开电源键拦截时，红键在应用层的行为

**这条测什么**：正文的挂机键 8 场景默认"开着拦截"。不开拦截时，应用自己对红键还有一套处理——这台机器的红键发的是 `ENDCALL` 键码时才看得到（发 `POWER` 的机器看不到，请对照附录 C 的 C17）。

**前提**：电源键拦截 =「关闭拦截」。

**怎么做与应该看到**：

- 在功能表 / 设置 / 应用程序等**子页面**按红键 → **回待机屏**（不锁屏）。
- 在**待机屏**按红键 → **锁屏**，而且是**抬手那一瞬间才锁**（按住不锁）。

### 6.5 通用选项弹窗的精确按键规则

#### 【补充-14】选项弹窗：挂机键也能关、上下循环、硬编码键码优先

### 6.9.1 从浏览器点 .jad 链接装 JAR

#### 【补充-37】在浏览器里点开一个 .jad 链接

**这条测什么**：不经过文件管理器、也不经过桌面，直接在浏览器里点一个 http/https 的 `.jad` 链接，是不是也走本应用的安装流程。【补充-05】只写了「文件管理器点开 .jar/.jad」这一条（file/content 协议），漏了浏览器点链接这条路。

**怎么做**：在浏览器里打开一个提供 J2ME 应用的网站，点一个 `.jad` 下载链接（如果系统问“用什么应用打开”，选本应用）。

**应该看到**：直接进入安装流程——和「应用程序 → 安装 → 选文件」一模一样的诺基亚风格安装弹窗（正在加载 → 正在安装 → 完成/失败，各阶段文案见【应用程序-02】）。装完回到「应用程序」页，列表里多出这个 JAR。

**通过标准**：能装、不闪退、装完列表里有。

**千万别当成 bug**：有些浏览器会先把 `.jad` 下载到本地再打开，这种情况下实际走的是 file 协议（和【补充-05】同一条路）；只有浏览器**直接**把 http/https 的 .jad 交给本应用时，才是在测这一条。两种路径装出来的 JAR 没区别。

**需要什么条件**：网络；一个能点开的 .jad 链接；存储权限。

**我的依据**：`AndroidManifest.xml` 里 `J2meLoaderActivity` 声明了 `text/vnd.sun.j2me.app-descriptor` + `http`/`https` scheme 的 intent-filter。

### 6.9.2 通知中心的“清除”项对不可清除通知会灰显

#### 【补充-38】“清除”和“全部清除”什么时候能用、什么时候灰掉

**这条测什么**：通知中心选项菜单里“清除”这一项不是随时都能点的——有些通知系统标记为“不可清除”，这时这一项会**灰显**，按不动。【通知中心-02】只写了“清除=清当前高亮那一条”，没写这个灰显规则。

**从哪开始**：通知中心（待机屏点通知条 / 功能表“通知中心”格子 / 设置→系统与权限→通知中心，三个入口任选）。

**怎么做一（“清除”灰显）**：高亮一条**不可清除**的通知（比如系统里某些前台服务通知、或正在通话中的通知），按左软键「选项」。

**应该看到**：菜单里「清除」这一行**颜色变淡、按确认键没反应**（被禁用）；「全部清除」和「通知设置」照常可用。

**怎么做二（“清除”可用）**：高亮一条**可清除**的普通通知，按左软键「选项」。

**应该看到**：「清除」这一行正常亮着，按确认键能清掉这一条。

**怎么做三（“全部清除”灰显）**：把通知列表清空（或本来就没有通知），按左软键「选项」。

**应该看到**：「全部清除」**灰显**、按不动（因为没东西可清）；列表空了自然没「清除」这一项。

**怎么做四（未授权时的灰显）**：没授通知使用权时进通知中心，按左软键「选项」。

**应该看到**：「全部清除」灰显；菜单里多一项「去授权」（已授权时不显示这一项）。

**通过标准**：四种情况下灰显/可用状态都对得上；灰显项按确认键确实没反应（不是“点了报错”）。

**千万别当成 bug**：「清除」灰显不是坏了——是系统说这条通知不能由用户手动清（比如通话中、前台服务），本应用跟着系统的标记走。

**我的依据**：`KeydroidxNotificationCenterFragment.showOptionsMenu()`——「清除」项的 enabled 标志是 `item.clearable`，「全部清除」的 enabled 标志是 `granted && !current.isEmpty()`，「去授权」只在未授权时才加进菜单。

#### 【补充-39】在「adb shell 本身就是 root」的设备上做 adb 激活（重点）

**这条测什么**：`adb shell` 的身份**不是恒定的 shell(uid=2000)**——设备被 Magisk/ROM 定制成 adbd 不降权时，从电脑 `adb shell` 进去就是 **root(uid=0)**。此时照「adb 激活」页给的命令启动服务端，服务端就是 root 身份，与「mini_shizuku 模式」期望的 shell 身份不符。**要验证这种设备上 App 有没有给用户可执行的出路**。

**从哪开始**：先在电脑上确认本机 adb 身份——`adb shell id`，输出 `uid=0(root)` 即命中本场景（普通手机是 `uid=2000(shell)`，不会出现本条问题）。

**怎么做**：手机 App → mini_shizuku → 选中「mini_shizuku 模式」→ 进「adb 激活」页 → 在电脑执行页面上给的命令（`adb shell sh /sdcard/Android/data/io.github.cctyl.nokia.debug/files/mini_shizuku.sh`）→ 回 App 按「刷新」。

**应该看到**：按 adb 激活指引操作后，**要么身份一致可用，要么给出真正可执行的下一步**，例如：

1. 激活时探测本机 adb shell 身份，是 root 就明确提示「本机 adb 为 root，请改用 **root 模式**激活」并给一键跳转；或
2. 提供 shell 身份的启动变体（如 `adb shell su 2000 -c "sh …/mini_shizuku.sh"`），让 adb 模式在 root 机上也能用；或
3. 至少把「请重新激活」改成区分场景的可执行文案（离线→请激活；身份不符→请改用 root 模式）。

**通过标准**：不允许出现「服务在线 + 身份不符 + 只能"重新激活"」的死局；失败提示必须给出用户可执行的下一步。

**我的依据**：`ShizukuFragment.updateStatusText()` 写死「✗ 与模式不符，请重新激活」；`KeydroidxFreezeManager.isServerChannelUsable()` 在 mini_shizuku 模式下**只接受 uid=2000**、root 身份直接跳过通道（日志「不暗中动用 root 能力」）；`KeydroidxSettingsStorage.getAuthMode()` 注释「模式是用户期望的服务端身份，实际以 WHOAMI 探测为准」。

**与其他手机的区别**：普通未 root 手机上 `adb shell` 被 adbd 降权为 uid=2000，同样的命令激活出来就是 shell 身份，一切正常——所以这条**只在"adb 不降权"的设备上才会暴露**，属环境相关缺陷，必须在用例里固定下来，避免下次换台 root 机又漏测。

### 6.9.3 按键反馈音（查漏补缺）

#### 【补充-40】按键反馈音：物理键 vs 虚拟键盘

**这条测什么**：按下按键时的声音 / 震动反馈，哪些地方有、哪些地方没有。

**怎么做与应该看到**：
