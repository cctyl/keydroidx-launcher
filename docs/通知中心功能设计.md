# 通知中心功能设计

**状态**：设计稿，待评审
**适用范围**：原键桌面 `ru.playsoftware.j2meloader.nokia.*`
**UI 原型**：`prototypes/notification_center.html`（页面本体）、`prototypes/notification_entry.html`（入口设计）
**规范依据**：`docs/FEATURE_PHONE_UI_SPEC.md`（§6 焦点、§8 布局、§15 选项菜单、§16 对话框、§39 空状态、§41/§42 破坏性操作）、`docs/NOKIA_DEVELOPMENT_RULES.md`

---

## 1 背景与目标

安卓通知要下拉状态栏才能看，按键机没有下拉手势，等于通知不可达。本方案让桌面直接读取系统通知，用功能机风格的列表页展示并支持清除，**完全不需要下拉动作**。

目标：

1. 通知可读、可打开、可单条/全部清除，全部用方向键 + 软键完成；
2. 从桌面到通知列表的按键路径最短（**Home → ↓ → 确认**）；
3. 无通知时不改变现有桌面布局，不给桌面增加常驻占位；
4. 不抢现有软键语义（左软键仍为功能表、右软键仍为桌面设置）。

---

## 2 方案总览：三层入口，本次做前两层

| 层级 | 入口 | 操作路径 | 本次范围 |
|---|---|---|---|
| 兜底 / 可发现 | 功能表格子 | 左软键 → 功能表 → 通知中心 | ✅ 阶段一 |
| 主路径 | 桌面通知条 | Home → ↓（移到通知条）→ 确认 | ✅ 阶段二 |
| 进阶 | 按键直达（任意界面按绑定键） | 一步 | ❌ 本次不做 |
| 不采用 | 顶部快捷栏加图标 | — | ❌ 挤占用户自定义栏位 |
| 不采用 | 桌面设置子项作为主要入口 | — | ❌ 层级太深，与「快捷」矛盾 |

**实施顺序**：数据层（两阶段共用，先做）→ 阶段一 功能表格子 → 阶段二 桌面通知条。

选择先做功能表格子的理由：改动面最小、可独立验收，先把页面和数据层跑通并暴露真实数据问题（权限、图标、时间格式、清除是否生效），再动桌面焦点体系这种高风险区域。

> 按键直达需要改 `NokiaKeyBinding` 的 6 处并行结构（`ACTION_*` 常量、`ACTION_COUNT`、`PREF_KEYS`、`DEFAULT_KEYCODES`、`getActionName()`、`dispatchDialogKey()` switch）+ `NokiaDesktopActivity.dispatchActionToHost()` 分支，成本明显更高，本次不做，设计预留。

## 3 数据层（两阶段共用，先行）

### 3.1 现状

- `NokiaNotificationListenerService.java:17` 是一个**空壳** `NotificationListenerService`，存在的唯一目的是为 `MediaSessionManager.getActiveSessions` 提供身份校验（读音乐播放状态），**没有任何通知相关实现**。
- Manifest 已注册：`AndroidManifest.xml:260-264`，含 `BIND_NOTIFICATION_LISTENER_SERVICE`。
- 授权状态判断与授权引导弹窗已就绪：`NokiaMusicSessionReader.isNotificationListenerEnabled(ctx)`、`NokiaMusicSessionReader.showGrantPrompt(...)`（桌面上已在用，见 `NokiaDesktopFragment.java:1155` `maybePromptNotificationAccess()`）。
- 授权弹窗开关位：`NokiaSettingsStorage.KEY_NOTIFY_ACCESS_PROMPT_DISABLED`（`NokiaSettingsStorage.java:550`）。

结论：**不需要新增 Service、不需要改 Manifest、不需要重写授权流程**，只需给现有 Service 补实现并加一个仓储类。

### 3.2 新增职责

**`NokiaNotificationListenerService`**（在现有类上扩展，不新建）

- 重写 `onListenerConnected()`：置位「已连接」，主动拉一次快照并通知仓储；
- 重写 `onNotificationPosted(StatusBarNotification)` / `onNotificationRemoved(StatusBarNotification)`：增量更新仓储并回调订阅者；
- 提供静态 `cancel(key)` / `cancelAll()`，内部走 `cancelNotification(String key)`（API 21+）；**API 19（minSdk=19，targetSdk=34）只能用已废弃的 `cancelNotification(pkg, tag, id)`**，需 `SDK_INT >= 21` 守卫（符合 `NOKIA_DEVELOPMENT_RULES.md` 的 API 19 兼容要求）；
- 服务未连接时清除请求直接返回失败，页面给出提示，不静默吞掉。

**新增 `NokiaNotificationRepository`**（进程内单例）

| 能力 | 说明 |
|---|---|
| 快照缓存 | 持有 `List<NokiaNotificationItem>`，避免每次进页面都跨进程拉取 |
| 订阅/回调 | `addListener/removeListener`，页面与桌面通知条订阅同一份数据 |
| 排序 | `postTime` 倒序（最新在前） |
| 过滤 | 默认排除本应用包名（避免自家保活通知进列表）；`FLAG_ONGOING_EVENT` 常驻通知默认隐藏（设置项可开） |
| 图标 | 优先复用 `NokiaS60IconMap.getIcon(pkg, label)` 走 S60 图标；未命中回退 `PackageManager.getApplicationIcon()` |
| 时间格式 | 今天 `HH:mm` / 昨天 / `M月d日` |
| 刷新节流 | `onNotificationPosted` 高频触发，主线程 200ms 合并刷新一次，避免刷屏时列表抖动 |

**`NokiaNotificationItem`**（数据模型）：`key`、`pkg`、`appName`、`title`、`text`、`postTime`、`iconDrawable`、`unread`、`clearable`、`contentIntent`。

> 未读标记是本应用自己维护的（`StatusBarNotification` 没有未读概念）：进页面视为已读，未读数 = 页面未打开期间新增的通知数。**实现为进程内存态水位线**（`lastReadTime`）：通知本身重启后不留存，水位线不持久化，进程重启归零可接受。

### 3.3 未授予通知使用权时的降级

页面顶部显示说明条 + 「去授权」入口（复用 `NokiaMusicSessionReader.showGrantPrompt()`），列表区显示空状态「未获得通知使用权」。**不隐藏入口**，保证用户知道功能存在及如何开启。

## 4 阶段一：功能表格子（可发现入口）

### 4.1 改动点

| 文件 | 位置 | 改动 |
|---|---|---|
| `NokiaAppItem.java` | `:13-16` | 新增 `TYPE_NOTIFICATION = 5`（现有 TYPE 为 APP=0 / BOX=1 / SETTINGS=3 / MAIN=4，2 号已废弃空出） |
| `NokiaMenuFragment.java` | `:613` 之后 | 追加 `result.add(new NokiaAppItem(NokiaAppItem.TYPE_NOTIFICATION, "通知中心", notifIcon, null))`，排在「桌面设置」之后 |
| `NokiaMenuFragment.java` | `:1133` `TYPE_SETTINGS` 分支之后 | 新增 `if (item.type == NokiaAppItem.TYPE_NOTIFICATION) { host.openNotificationCenter(); return true; }` |
| `NokiaDesktopActivity.java` | `:653` `openDesktopSettings()` 附近 | 新增 `openNotificationCenter()` → `switchFragment(new NokiaNotificationCenterFragment())` |

### 4.2 图标（已定）

nokia-common 的 `NokiaIcons` 原有 `NOTIFICATIONS = "\uE7F4"`（谷歌 Material notifications 铃铛），本次已补 `ICON_NOTIFICATIONS` / `ICON_NOTIFICATIONS_OFF` 兼容别名（keydroidx-core 仓库，`includeBuild` 源码替换）。功能表入口直接用 `NokiaIcons.get(ctx, ICON_NOTIFICATIONS, ...)` 生成字体图标，**无新增 vector 资源**，规避 API 19 矢量图崩溃问题。

### 4.3 未读角标

功能表格子上的未读数字角标需要与网格 cell 渲染逻辑耦合，本阶段**不做**，留给阶段二与桌面通知条一并处理（避免两次改网格渲染）。本阶段格子显示为普通入口。

### 4.4 无通知时行为

入口常驻可见，点击进入后由页面展示空状态。理由：入口位置固定才能形成肌肉记忆，忽隐忽现的入口违背规范 §5 的一致性要求。

## 5 阶段二：桌面通知条（主路径）

### 5.1 布局

`fragment_nokia_desktop.xml`（当前结构：`:61` `shortcutDivider` → `:70` `notificationArea` → `:84` `quickToggleDivider` → `:92` `quickToggleScroll`）：

- 在 `:67` 之后新增通知条容器 `notifBarContainer`（`LinearLayout`，高度约 24dp，默认 `GONE`）；
- `:70` `notificationArea` 的 `layout_below` 由 `@id/shortcutDivider` 改为 `@id/notifBarContainer`；
- 无通知时容器 `GONE`，`notificationArea` 上移，桌面布局与现状**完全一致**（不占空间、不挤压组件区）。

通知条内容（单行）：铃铛图标 + 「N 条未读通知」+ 最新一条摘要（单行 `ellipsize=end`）+ 未读数字角标。

尺寸换算一律走 `NokiaDimens.dp()`，禁止裸写 px；分隔线走 `NokiaDashedLineDrawable`。

### 5.2 焦点体系改造（本次最大风险点）

现状：`focusTargets` 的构造顺序是 **快捷栏 → 组件区 → 快捷开关**（`NokiaDesktopFragment.java:403-435`，组件由 `:1949` `collectWidgetTargets()` 收集），分区靠索引硬算：

```java
shortcutLast()  = shortcutCount                      // :2016
widgetFirst()   = shortcutCount                      // :2017
widgetLast()    = shortcutCount + widgetCount        // :2018
toggleFirst()   = shortcutCount + widgetCount        // :2020
```

插入通知条作为**第 2 个焦点区**后，所有 helper 必须改为累加式：

```java
shortcutLast() = shortcutCount;
notifFirst()   = shortcutCount;
notifLast()    = shortcutCount + notifBarCount;      // notifBarCount = 0 或 1
widgetFirst()  = notifLast();
widgetLast()   = widgetFirst() + widgetCount;
toggleFirst()  = widgetLast();
toggleLast()   = toggleFirst() + toggleCount();
```

并同步修改：

- `isInShortcuts()/isInWidgets()/isInToggles()`（`:2023-2025`）新增 `isInNotifBar()`；
- `moveUp()`（`:2027`）、`moveDown()`（`:2052`）、`moveLeft()`（`:2081`）、`moveRight()`（`:2104`）每个分支补通知条的进出规则（通知条为单行，LEFT/RIGHT 保持不动返回 false，与组件区行为一致）；
- **`refreshWidgetRows()` 中 `:574-576` 的焦点裁剪逻辑**：它把快捷项之后的焦点全部删除再重建，必须同步处理通知条，否则通知条焦点会被抹掉或重复添加；
- 快捷栏重建（`:403` `focusTargets.clear()`）后要重新插入通知条焦点。

> 这块索引计算是硬编码的整数区间，改动面小但极易出错。实施时必须连带回归验证：快捷栏 / 组件 / 开关三区的方向键循环跳转是否与改动前一致（无通知时 `notifBarCount=0`，行为应完全等价）。

### 5.3 按键语义

| 按键 | 通知条聚焦时 |
|---|---|
| ↑ / ↓ | 跨区移动焦点（快捷栏 ⇄ 通知条 ⇄ 组件 ⇄ 快捷开关） |
| ← / → | 保持不动（单行） |
| 确认键 | 进入通知中心，焦点自动落在**最新一条** |
| 左软键 | 功能表（**不变**） |
| 右软键 | 桌面设置（**不变**） |

长按确认键「全部清除」为可选增强，本次不做。

### 5.4 刷新时机

- 桌面 `onResume`（回到桌面时重新拉快照）；
- 仓储变更回调（新通知 / 通知被移除）；
- 通知中心内清除后（回到桌面立即同步）。

## 6 通知中心页面

### 6.1 页面契约

```
screenId:        notifications.center
根布局:          fragment_nokia_notification_center.xml（根宽 240dp，高 match_parent）
基类:            NokiaPageFragment（isTopAlign=true，复用 scaleMidContent / 主题 / 底栏装配）
title:           通知中心
初始焦点:        第 1 条（最新）；空列表时无焦点
focusOrder:      列表项自上而下
LSK:             选项
CENTER:          打开该通知
RSK:             返回
BACK:            返回桌面
```

### 6.2 列表项结构

单行双信息，高度约 44dp：

```
[App图标]  应用名              时间
           标题（主）
           正文摘要（次，单行省略）
```

- 焦点：实心黄色高亮条（与功能表/组件设置一致），反白文字；未读左侧蓝色小圆点；
- 滚动：焦点先动、视口跟随（规范 §45），滚动辅助复用基类 `NokiaPageFragment.smoothScrollToVisible()`；
- 分隔：行间点线 `NokiaDashedLineDrawable`。

### 6.3 操作

| 操作 | 实现 |
|---|---|
| 打开 | `contentIntent.send()`，try/catch 包裹；失败（权限/已失效）给 Toast「无法打开该通知」 |
| 单条清除 | 选项弹窗 → 清除 → `NokiaNotificationListenerService.cancel(key)`；不可清除的通知（`clearable=false`）选项置灰禁用 |
| 全部清除 | `cancelAllNotifications()`，**先弹二次确认**，默认焦点在「取消」，破坏性操作用明确动词（规范 §41/§42） |
| 通知设置 | 跳转桌面设置 → 系统与权限 → 通知中心 |

选项弹窗复用 `NokiaOptionsDialog.show(fm, title, items)`（`:100`），`OptionItem` 支持 `enabled=false` 置灰跳过。二次确认**已定：复用 `NokiaOptionsDialog` 承载**——标题「全部清除？（N 条，无法撤销）」，「取消」放第一位（该弹窗默认聚焦第一项，天然满足「默认焦点在安全选项」）。

### 6.4 状态

- **空状态**：「没有通知」+「新通知会显示在这里」（规范 §39）；
- **未授权**：说明条 + 去授权入口 + 空状态；
- **加载中**：进入时若仓储尚未连接，顶部显示「读取中...」。

## 7 设置项

桌面设置 → **系统与权限**（`NokiaSettingsGroupFragment.GROUP_SYSTEM`）新增一项「通知中心」：

- 通知使用权状态 + 一键授权入口；
- 「桌面显示通知条」开关（默认开）；
- 「显示常驻通知」开关（默认关，隐藏 `FLAG_ONGOING_EVENT` 类通知）。

改动点：`NokiaSettingsGroupFragment.iconsOf()`（`:76-80`）、`namesOf()`（`:93-95`）两个**并行数组** + `NokiaDesktopSettingsFragment.GROUP_SYSTEM` 的 `onSelectSystem()` 分支 + 新增 `NokiaNotificationSettingsFragment`。

新增持久化键（写在 `NokiaSettingsStorage`，PREFS 为 `nokia_desktop_settings`）：`KEY_NOTIFICATION_BAR_ENABLED`、`KEY_NOTIFICATION_SHOW_ONGOING`、`KEY_NOTIFICATION_UNREAD_COUNT`。

## 8 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 桌面焦点索引改造 | 方向键跳转错乱（**最高风险**） | 累加式 helper 重写；`notifBarCount=0` 时必须与现状行为完全等价；逐区回归 |
| API 19 清除 API 差异 | 低版本无法清除 | `SDK_INT>=21` 走 `cancel(key)`，否则 `cancel(pkg, tag, id)`；失败给明确提示 |
| 通知使用权未授予 | 功能不可用 | 不隐藏入口，页面内引导；设置项常驻授权入口 |
| `contentIntent` 失效 | 点击无反应 | try/catch + Toast，不崩溃 |
| 刷屏通知（如下载进度）刷新风暴 | 列表抖动/卡顿 | 200ms 合并刷新 + 同 key 覆盖更新 |
| 自家保活通知混入 | 列表里出现自己的通知 | 按包名过滤（本应用包名），与保活通知常驻策略无关 |
| nokia-common 无铃铛图标 | 图标缺失 | 本地 drawable 兜底，注意 API 19 矢量图问题 |
