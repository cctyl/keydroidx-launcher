# 触屏模式虚拟键盘双窗口解耦架构与设计文档

## 一、背景与设计目标

### 1.1 业务背景
KeydroidX Launcher 最初完全面向实体按键机（如展锐/联发科九宫格功能机）设计，整个交互模型高度依赖标准物理按键（LSK/RSK/D-Pad/数字键/绿键/红键）。为了拓展使用场景，使得在全触屏智能手机、备用机或没有物理键盘的设备上也能完整体验功能机生态并畅玩 J2ME (JAR) 游戏，项目引入了**“触屏模式（Touch Screen Mode）”**。

### 1.2 核心设计目标与约束原则
1. **物理机主干零污染（绝对第一原则）**：
   - 物理按键机是本生态的核心根基。触屏模式的所有逻辑必须严格受开关控制；
   - 在非触屏模式下，业务代码、窗口尺寸、按键分发与渲染逻辑保持 100% 纯净，零侵入、零性能与显存开销。
2. **彻底解耦，杜绝“测一个改一个”**：
   - 虚拟键盘必须独立于具体的业务界面。无论是在桌面（`KeydroidxDesktopActivity`）、JAR 模拟器（`MicroActivity`）还是任何弹窗，严禁在每一个界面的 XML 布局中强行插入键盘视图；
   - 采用系统级**双窗口视窗隔离（Dual-Window Decoupling）**架构，使业务窗口与键盘窗口在操作系统 Window 层面物理分离。
3. **消除两套虚拟键盘重叠冲突**：
   - J2ME-Loader 引擎原生自带有透明浮层软键盘；当开启我们的实体风格虚拟键盘时，原生键盘必须在配置层、UI 层和引擎底层实现三重强制互斥，绝对不发生视觉重叠。
4. **全屏沉浸感与按键无遮挡**：
   - 触屏模式下自动沉浸式隐藏 Android 系统底部的“三大金刚按键”（菜单、Home、返回），避免系统栏阻挡底行按键（`*`、`0`、`#`）；
   - 弹窗（Dialog）从打开到关闭全生命周期内，系统导航栏必须保持 0 毫秒闪烁；弹窗自身必须悬停在键盘正上沿，绝不遮挡键盘。

## 二、架构演进与方案对比

### 2.1 传统方案的缺陷（为什么推翻“布局内嵌键盘”）
最初的尝试是将虚拟键盘作为 `<include layout="@layout/keydroidx_virtual_keypad" />` 塞入 Activity 的 XML 根布局中：
- **致命缺陷 1（无限适配）**：桌面做了一遍，进入 JAR 游戏（`MicroActivity`）又要再做一遍；未来如果有独立子应用，必须处处 include；
- **致命缺陷 2（弹窗被遮挡）**：Android 系统的 `Dialog` 是具有独立物理全屏坐标系的 Window。每次弹出 Dialog，它都会默认贴在整块手机物理屏幕的底端，从而把布局内的键盘完全盖死；
- **致命缺陷 3（焦点与事件混乱）**：键盘和业务 View 挤在同一个窗口中，Dialog 弹出时的暗色遮罩和模态机制会导致键盘无法被触摸按下，事件分发陷入层层中转与击穿底层页面的恶性循环。

### 2.2 现代架构选择：双窗口彻底解耦（Dual-Window Architecture）
通过 Android 系统底层的 Window 机制，将整块屏幕划分为上下两个完全独立的平行 Window：

```text
┌────────────────────────────────────────────────────────┐
│               Android 操作系统显示服务 (WMS)             │
├────────────────────────────────────────────────────────┤
│ 【窗口 A：业务主屏 Window（上半屏）】                    │
│  - 宿主：KeydroidxDesktopActivity / MicroActivity       │
│  - 边界：Gravity.TOP，height = screenHeight - keypadH  │
│  - 特性：获得系统 Window 输入焦点，纯粹承载页面与游戏    │
│  - 附带：所有业务 Dialog 均停靠在此窗口可视区域内       │
├────────────────────────────────────────────────────────┤
│ 【窗口 B：独立虚拟键盘 Window（下半屏）】               │
│  - 类型：TYPE_APPLICATION_PANEL（应用内子窗口，免权限） │
│  - 边界：Gravity.BOTTOM，height = 310dp (自适应测量)   │
│  - 特性：FLAG_NOT_FOCUSABLE，绝不争抢输入焦点          │
│  - 职责：只负责渲染按键并在触摸时直接向前台注入 KeyEvent │
└────────────────────────────────────────────────────────┘
```

## 三、核心技术实现细节

### 3.1 统一调度中枢：`KeydroidxTouchWindowController`
整个触屏双窗口模式的逻辑全部收敛于单一控制器 `KeydroidxTouchWindowController.java`，业务 Activity 仅需在生命周期内挂载 1~2 行代码。

#### 1. 物理屏幕总高计算（`getScreenTotalHeight`）
标准 `DisplayMetrics.heightPixels` 会剔除隐藏的系统导航栏区域。必须使用底层 API 获取整块物理屏幕的实际像素高：
```java
public static int getScreenTotalHeight(Context context) {
    WindowManager wm = (WindowManager) context.getSystemService(Context.WINDOW_SERVICE);
    if (wm != null) {
        Point point = new Point();
        wm.getDefaultDisplay().getRealSize(point);
        return point.y;
    }
    return context.getResources().getDisplayMetrics().heightPixels;
}
```

#### 2. 上半屏主业务窗口压缩（`applyActivityWindowBounds`）
当触屏模式开启时，动态重设 Activity Window 的 LayoutParams：
- `params.gravity = Gravity.TOP | Gravity.CENTER_HORIZONTAL;`
- `params.height = screenHeight - keypadHeightPx;`
- **效果**：系统 WMS 认为此 Activity 的可用物理高度仅为上半屏，顶栏在顶部，底栏紧靠在键盘上沿，游戏 Canvas 自动按上半屏等比缩放。
- 关闭触屏模式时，重设 `params.gravity = Gravity.FILL; params.height = MATCH_PARENT;`，物理机全屏无感恢复。

#### 3. 独立按键窗口挂载（`attachKeypadWindow`）
在 Activity 的 `decorView.post(...)` 中挂载子 Window：
- **窗口类型**：`WindowManager.LayoutParams.TYPE_APPLICATION_PANEL`（附属于 Activity 的 DecorView Token，完全无需 `SYSTEM_ALERT_WINDOW` 悬浮窗系统权限）；
- **核心 Flags**：
  - `FLAG_NOT_FOCUSABLE`：不争抢焦点，确保按键按下时焦点始终留在上半屏的游戏/桌面上；
  - `FLAG_LAYOUT_IN_SCREEN | FLAG_LAYOUT_NO_LIMITS`：突破边距限制，贴紧屏幕最下端；
- **动态测量自适应**：
  为避免不同设备 DPI 下底部按键被裁切，在 `addView` 前调用 `keypadContainer.measure()`，以布局实测的 `measuredHeight`（约 310dp）作为窗口精确高度，确保功能岛、123、456、789、`*`0`#` 全数 100% 完整显示。

## 四、沉浸式全屏与“三大金刚按键”闪现根除方案

### 4.1 顶部状态栏与底部金刚键控制
在触屏模式下，必须同时隐藏顶部的 Android 原生状态栏与底部的系统导航栏：
```java
public static void applyImmersiveNavigationBars(Window window, boolean touchMode) {
    if (window == null) return;
    window.addFlags(WindowManager.LayoutParams.FLAG_FULLSCREEN);

    if (touchMode) {
        if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.R) {
            window.setDecorFitsSystemWindows(false);
            WindowInsetsController controller = window.getInsetsController();
            if (controller != null) {
                controller.hide(WindowInsets.Type.statusBars() | WindowInsets.Type.navigationBars());
                controller.setSystemBarsBehavior(WindowInsetsController.BEHAVIOR_SHOW_TRANSIENT_BARS_BY_SWIPE);
            }
        }
        if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.KITKAT) {
            View decor = window.getDecorView();
            if (decor != null) {
                int flags = View.SYSTEM_UI_FLAG_FULLSCREEN
                        | View.SYSTEM_UI_FLAG_HIDE_NAVIGATION
                        | View.SYSTEM_UI_FLAG_IMMERSIVE_STICKY
                        | View.SYSTEM_UI_FLAG_LAYOUT_FULLSCREEN
                        | View.SYSTEM_UI_FLAG_LAYOUT_HIDE_NAVIGATION
                        | View.SYSTEM_UI_FLAG_LAYOUT_STABLE;
                decor.setSystemUiVisibility(flags);
            }
        }
    }
}
```

### 4.2 为什么弹窗操作时金刚键会闪现？
1. **打开弹窗时闪现**：
   - 若在 `dialog.show()` 之后才设置沉浸式，在 `show()` 到代码执行之间存在 16ms 延迟，WMS 收到无沉浸标志的 Dialog 会先弹出金刚键，再缩回。
   - **根治方案**：在 `dialog.show()` **之前**（如 `onCreate` / `onCreateDialog`）预先注入沉浸式 Flags。
2. **关闭弹窗（RSK / dismiss）瞬间闪现**：
   - 当点击 RSK 执行 `dialog.dismiss()` 时，Dialog 窗口被销毁，焦点移交回 Activity。在过渡期内 SystemUI 尝试恢复导航栏，随后 Activity 重新获得焦点再压回，形成肉眼可见的“闪烁”。
   - **根治方案一（Pre-Dismiss 平滑交接）**：在 `dismiss()` 被调用的瞬间，先为 Dialog Window 加上 `FLAG_NOT_FOCUSABLE`，平滑交接焦点，阻止 SystemUI 启动恢复动画；
   - **根治方案二（Activity 实时拦截）**：在 Activity 挂载 `OnSystemUiVisibilityChangeListener`，一旦检测到导航栏有弹起倾向，同一帧内立即压回。

## 五、所有弹窗（Dialog）的统一抬升与穿透架构

### 5.1 弹窗精准抬高（`params.y = keypadHeightPx`）
在触屏模式下，所有的弹窗 Window 自动配置：
- `window.setGravity(Gravity.BOTTOM | Gravity.CENTER_HORIZONTAL);`
- `params.y = keypadHeightPx;`
- **效果**：弹窗不再贴着物理屏幕底边，而是精准坐在虚拟键盘的上沿（停留在上半屏），底部的“选择/返回”文字清晰可见，绝不覆盖键盘。

### 5.2 消除遮罩与开启非模态触摸穿透
Dialog 默认的全屏暗色遮罩（DIM）与模态独占会拦截落在键盘上的触摸。
必须在控制器中强制注入：
```java
window.clearFlags(WindowManager.LayoutParams.FLAG_DIM_BEHIND);
params.flags &= ~WindowManager.LayoutParams.FLAG_DIM_BEHIND;

window.addFlags(WindowManager.LayoutParams.FLAG_NOT_TOUCH_MODAL);
params.flags |= WindowManager.LayoutParams.FLAG_NOT_TOUCH_MODAL;
```
- **效果**：键盘表面没有任何黑灰阴影，且手指触摸键盘时，触摸事件直接穿透到达虚拟键盘进行触发。

### 5.3 按键事件直达前台 Dialog
当屏幕上有弹窗时，虚拟键盘在 `sendKeyToForeground` 中持有当前活跃 Dialog 的引用：
- **跳过 Activity 中转**：直接执行 `activeDialog.dispatchKeyEvent(event)`；
- 弹窗的 `OnKeyListener` 收到标准键码后直接执行：
  - RSK (`KEYCODE_SOFT_RIGHT` / `KEYCODE_BACK`) -> 直接关闭弹窗；
  - LSK (`KEYCODE_SOFT_LEFT` / `KEYCODE_DPAD_CENTER`) -> 直接触发选项；
  - 方向键 (`KEYCODE_DPAD_UP` / `KEYCODE_DPAD_DOWN`) -> 列表上下移动焦点。

## 六、JAR 模拟器（`MicroActivity`）与 J2ME 虚拟键盘互斥联动

### 6.1 游戏内键盘常驻
在 `javax.microedition.shell.MicroActivity` 的生命周期中对称挂载：
- `onResume()`:
  - `KeydroidxTouchWindowController.applyActivityWindowBounds(this);`
  - `KeydroidxTouchWindowController.attachKeypadWindow(this);`
- `onPause()`:
  - `KeydroidxTouchWindowController.detachKeypadWindow(this);`
- **效果**：从桌面点击任何 JAR 启动后，游戏 Canvas 运行在上半屏，下半屏虚拟键盘岿然不动。按数字键、方向键、软键直接流入 J2ME 虚拟机事件循环；按绿键呼出复古挂机菜单，按红键一键挂机返回桌面。

### 6.2 J2ME-Loader 原生虚拟键盘三重互斥防护
为了彻底杜绝两套虚拟键盘重合：
1. **数据层批量更新（`syncTouchModeToJ2meProfiles`）**：
   开启触屏模式瞬间，后台异步将全局配置 `nokia_global` 以及所有已安装单应用 `config.json` 中的 `"ShowKeyboard"` 字段全量重写为 `false`；
2. **设置界面防呆（`ConfigActivity.java`）**：
   在触屏模式下打开“JAR 全局设置”，界面上的“虚拟键盘”Switch 强制显示为关闭（OFF），追加标注 `(已由触屏按键接管)` 并禁用点击；保存时强制 `params.showKeyboard = false`；
3. **引擎底层绝对阻断（`MicroLoader.applyConfiguration`）**：
   在 MIDlet 启动初始化时进行强校验：
   ```java
   boolean showVk = params.showKeyboard;
   if (KeydroidxSettingsStorage.isTouchMode(context)) {
       showVk = false; // 触屏模式下强制阻断 J2ME 浮层键盘
   }
   if (showVk) {
       ContextHolder.setVk(new VirtualKeyboard(params));
   } else {
       ContextHolder.setVk(null);
   }
   ```
   从引擎层 100% 杜绝了原生浮层键盘的加载。

## 七、架构总结与维护规范

| 维度 | 物理按键模式（主干） | 触屏键盘模式（独立外挂） |
| :--- | :--- | :--- |
| **主窗口高度** | 100% 全屏 (`MATCH_PARENT`) | 上半屏 (`screenHeight - 310dp`) |
| **独立按键 Window** | 不挂载 (`null`) | 贴底独立子窗口 (`TYPE_APPLICATION_PANEL`) |
| **系统三大金刚键** | 遵循系统默认状态 | 强制全屏沉浸隐藏 (`IMMERSIVE_STICKY`) |
| **弹窗 (Dialog) 位置**| 遵循系统贴底居中 | 精准抬升停靠在键盘上沿 (`y = 310dp`) |
| **J2ME 浮层键盘** | 允许用户自主配置 | 引擎层强行关闭互斥 |
| **业务布局代码侵入**| **0 侵入**（纯净 XML） | **0 侵入**（纯净 XML） |

### 后续开发注意规范：
1. **严禁在 Activity 布局中重新引入内嵌虚拟按键**；
2. **所有新建 Dialog 均应走 `KeydroidxDialogFocus` 或在 `onCreateDialog` 时调用 `KeydroidxTouchWindowController.applyDialogWindowBounds(dialog)`**；
3. **保持物理模式优先**：任何与触屏模式相关的视觉或布局修正，必须被包裹在 `if (KeydroidxSettingsStorage.isTouchMode(context))` 作用域之内。
