## 用户需求

用户发现程序在 240×320 分辨率下，桌面快捷应用栏上方点线变成实线、下方点线直接消失，320×480 及更高分辨率下正常。用户强调这**只是举例**，实际各界面远不止这两处分辨率问题。适配目标分级：**主适配 240×320 与 320×480 按键触屏机（必须逐界面验证通过），次要适配 16:9 现代长屏（布局不崩、不变形、不裁切、可正常操作即可）**。

## 澄清结论

1. 修复范围：系统性修复——修已知问题 + 全界面走查找出未知问题 + 修复 + 沉淀设计规范。
2. 布局优先级：顶栏、快捷应用栏（含上下点线）位置优先保障、稳定可见；中间桌面组件区允许被挤压（后续会做可滚动），顶栏不做紧凑模式。
3. 计划必须包含**全界面走查审计闭环**，不能只修已知点。

## 产品概述

诺基亚风格安卓桌面启动器，以 240×320 dp 为设计基准、运行时整体缩放适配不同屏幕。本次不改变该架构，修复缩放体系下的渲染缺陷，通过双机走查建立问题清零闭环，并沉淀长效设计规范。

## 核心功能

- 修复 240×320 下快捷栏上点线变实线、下点线消失，两种分辨率下点线均清晰稳定
- 桌面布局弹性化：顶栏与快捷栏（含上下点线）固定，中间通知/组件区为可压缩弹性区，为后续滚动化铺路
- 修复按键绑定页 px 单位 bug、百宝箱布局 XML 属性错位 bug
- 统一尺寸换算工具类，消除 8 处复制粘贴的 dp() 方法，弹窗尺寸集中管理
- 全界面 × 双分辨率真机截图走查，登记问题清单并按严重度修复新发现问题
- 320×480 专项评估（顶栏比例、文字发虚、弹窗一致性）并入走查
- CODEBUDDY.md 沉淀《双分辨率设计规范》，含走查真实踩坑与新界面 checklist
- 修复后双机回归复验，16:9 长屏 push 安装包兜底确认不崩不裁切

## 实现方案

### 根因结论（已探明）

项目并非"没做适配"，而是「240×320 dp 设计稿 + KeydroidxBaseActivity 运行时 setScaleX/Y 整体缩放」架构下的实现缺陷叠加：

1. **点线变实线**：`KeydroidxDashedLineDrawable` 用 `DashPathEffect` + `ANTI_ALIAS_FLAG`，mdpi（240×320）下线宽仅 1px，dash 边缘被抗锯齿羽化糊成实线；硬件加速 Canvas 下 DashPathEffect 在 Android 4.4 有已知渲染缺陷（可画成实线或不渲染）。
2. **点线消失**：顶栏 wrap_content 实际偏高挤压 midPanel（240×320 下 midPanel < 262dp 设计高），触发 `scaleMidContent()` 二次缩小分支（约 277-279 行），1px 线经非整数缩放被采样掉。
3. **体系缺陷**：density 来源用了 `Resources.getSystem()` 绕过 attachBaseContext 修正；XML drawable 与代码覆盖双轨并存；8 处 dp() 复制；KeydroidxKeyBindFragment 用 px 写死尺寸。

### 修复策略（关键决策与权衡）

1. **虚线改 drawRect 点阵**（弃用 DashPathEffect）：draw() 中循环 `canvas.drawRect()` 画实心方块点（3dp 点 + 3dp 间隔，换算后下限 1px），FILL 样式无 AA 羽化，drawRect 硬件加速下全版本正常渲染。优于 setLayerType(SOFTWARE)（软绘制整 View 性能代价）。性能：单次约 40 次 drawRect 仅作背景，开销 O(宽度/点距)，可忽略。density 改由构造函数传入 Resources，消除 getSystem() 不一致。
2. **桌面布局弹性化**（消灭二次缩小）：`fragment_keydroidx_desktop.xml` 根布局由写死 240×262dp 改为宽 240dp、高 match_parent；快捷栏区（上点线+快捷栏+下点线）固定顶部；通知/组件区 `layout_below` 下点线填充剩余空间成弹性区。`KeydroidxBaseActivity.scaleMidContent()` 适配：内容高为 match_parent 时跳过二次缩小分支，仅按宽度 scale 变换。320×480 宽度缩放逻辑不变，行为不回退（组件区填充更多空间）。同步核对 `KeydroidxDesktopFragment` 名称气泡定位（约 643-665 行）与新坐标系一致性。
3. **统一尺寸工具类 KeydroidxDimens**：纯静态 dp 换算（`(int)(v*density)`，与原行为逐值一致），替换 8 处私有 dp() 复制；不持有 Context 防泄漏。
4. **Bug 修复**：KeydroidxKeyBindFragment 143-159 行 px 值改 KeydroidxDimens dp 换算；fragment_keydroidx_box.xml 的 scrollbars/fadingEdge/overScrollMode 移回 ScrollView 标签内；三个 dialog 的 28dp 等关键尺寸收敛至 dimens.xml（值不变，先集中后验证，截图异常再微调，避免过度设计）。
5. **全界面双机走查审计**（回应"远不止这两处"）：建立「界面 × 分辨率」走查矩阵——桌面（通知区/快捷栏/气泡/空与多快捷项状态）、功能表（含分页）、百宝箱、桌面设置、快捷栏设置、组件设置、组件类型选择、按键绑定、按键绑定向导、安装/卸载/选项弹窗。adb 逐界面导航截图（`am start` + `input keyevent/tap`），读图登记问题清单（现象+截图+严重度）落盘 `docs/分辨率走查问题清单.md`。320×480 专项（顶栏比例失调、文字发虚、弹窗一致性）并入走查项。需特定数据触发的界面尽量构造，无法构造的用代码审查兜底并注明。
6. **按清单修复新发现问题**：必修项（内容不可见/不可操作/明显错乱）全部修；观感项与用户确认后修。
7. **规范沉淀放在走查之后**：把走查真实踩坑写进 CODEBUDDY.md《双分辨率设计规范》，比预先写更有价值。

### 实施注意（执行细节）

- **不改动**「240 基准 + 整体缩放」中枢架构，**不引入**资源限定符目录（避免与代码缩放双轨冲突），定点修复。
- 弹性化涉及 scaleMidContent，须重点回归 320×480 与长屏（scale≠1 路径）；二次缩小分支触发处加 Log.d 日志，便于排查。
- 按项目规矩在关键节点补日志（缩放分支、走查关键操作）；不私自 git commit；不触碰 J2ME 模拟层（javax.microedition.* / org.microemu）。
- 走查与修复按「修一处→构建→装 4a24ecf 实测」迭代，以真机表现为准；Android 4.4 上所有 API 22+ 引用必须 SDK_INT 守卫。
- 构建：`.\gradlew.bat assembleOpenDebug`，产物 `app/build/outputs/apk/open/debug/J2ME_Loader-1.8.2-open-debug.apk`。设备：4a24ecf（240×320，USB 直装）、tcpip 设备（320×480，直装）、jz5dauzlu8euw4e6（小米长屏，仅 push 到 /sdcard/Download/ 由用户安装）。

## 架构设计

保持现有架构：`activity_nokia.xml`（顶栏 + midPanel + 底栏）→ `KeydroidxBaseActivity` 缩放中枢 → midPanel 内 Fragment。本次仅两点收口：**尺寸换算收口到 KeydroidxDimens**、**虚线绘制收口到 KeydroidxDashedLineDrawable（点阵实现）**；桌面 Fragment 布局从"固定设计稿高度"演进为"固定区 + 弹性区"模型，与未来组件区滚动化方向一致。
