## 1. 目标行为定义（术语约定）

本文档中「挂机键」指 物理电源键（KEY_POWER，keyCode=116）以及可能包含的home键，在诺基亚语义下被重定义为「红键/挂机键」：

| 场景                    | 第一次按下                                  | 第二次按下                                            | 第三次按下 | 
|---|---|---|---|
| 亮屏 + 任意非诺基亚应用  | 回诺基亚桌面）                               | 锁屏                                                  | 亮屏，显示锁屏界面，解锁后显示诺基亚桌面 |
| 息屏 + 任意非诺基亚应用  | 亮屏，显示锁屏界面，解锁后显示原本的应用        | 回诺基亚桌面                                          |  锁屏 |
| 亮屏 + 诺基亚桌面待机屏  | 锁屏（熄屏）                                 | 亮屏，显示锁屏界面，解锁后显示诺基亚桌面                 | 锁屏（熄屏）|

| 息屏 + 诺基亚桌面待机屏  |亮屏，显示锁屏界面，解锁后显示诺基亚桌面        | 锁屏（熄屏）                                            |亮屏，显示锁屏界面，解锁后显示诺基亚桌面 
| 亮屏 + 诺基亚桌面其他界面（功能表/设置/百宝箱） |  回到桌面待机屏（不锁屏） | 锁屏（熄屏）                                          |亮屏，显示锁屏界面，解锁后显示诺基亚桌面 
| 息屏 + 诺基亚桌面其他界面（功能表/设置/百宝箱） |  亮屏，显示锁屏界面，解锁后显示诺基亚桌面其他界面 | 回诺基亚桌面主界面              |锁屏（熄屏）
| 亮屏 + 锁屏界面 |  锁屏（熄屏）   | 亮屏，显示锁屏界面，解锁后原本显示什么就显示什么 |   回诺基亚桌面主界面 
| 息屏 + 锁屏界面 | 亮屏，显示锁屏界面，解锁后原本显示什么就显示什么 | 回诺基亚桌面主界面 |  锁屏

## 2. 结论速览（哪些可行 / 已验证）

| 方案 | 结论 | 实机验证程度 |
|------|------|-------------|
| **方案一** evdev grab + uinput 回放 | ✅ 可行（**推荐**） | **已跑通**：抓对设备 + `O_RDONLY` grab + uinput 回放 + 消费，决策状态机已实现并实机验证 |
| **方案二** evdev grab 纯消费（保底） | ✅ 可行 | 逻辑成立（uinput 不可用时自动降级，与方案一同实现） |
| **root 激活**（权限升级通道，非独立方案） | ✅ 已实现 | 实机验证：libsu 以 root 身份拉起服务端后，方案一 uinput 回放完整生效 |
| **方案四** 无障碍按键过滤 | ❌ **不可行，已作废** | 实测失败：无障碍 `onKeyEvent` **收不到电源键** |
| 早期「ENDCALL + 无障碍拉回」 | ❌ **已作废** | 目标键实为电源键而非 ENDCALL，方案未落地 |

**一句话总结**：挂机键拦截**必须走 evdev grab（方案一/二）**，无障碍方案从原理上就拦不到电源键。方案一已在这台安卓 13 机器上验证完整链路（抓对设备 + grab + uinput 回放 + 决策状态机 + 注入）。方案三已取消，root 不再作为独立拦截方案，而是作为「权限升级通道」激活 mini_shizuku 服务端，使方案一完整生效（详见第 7.2 节）。

## 3. 已验证的关键事实（勿再推翻）

1. **`O_RDONLY` + `EVIOCGRAB` 可行**：只读打开 `/dev/input/eventX` 后执行 `EVIOCGRAB` 成功（SELinux enforcing 下也必须只读，`O_RDWR` 会失败）。这与 KeyMapper 的 `grabbed_device.rs` 实现完全一致。
2. **uinput 虚拟设备创建成功**：本机（安卓 13，C65GA202401021974）shell 有 `/dev/uinput` 写权限，回放设备建立成功。
3. **正确设备是 `event1`/`gpio-keys`**：早期实现抓错设备（`event5`/`qpnp_pon` 不是物理电源键所在设备），修复后能正确抓到物理电源键设备。
4. **拦截+消费链路真机跑通**：开启 mini_shizuku「电源键拦截」后按挂机键，确实从桌面退出（被拦截消费）——用户实测确认。
5. **KeyMapper 拦 power 键用的是 evdev grab + root/shell，不是无障碍**（源码证据见第 8 节）。
6. **无障碍 `onKeyEvent` 收不到电源键**：电源键由 `InputDispatcher`/`PhoneWindowManager` 在更早层级消费，系统不派发给无障碍服务做按键过滤——方案四从一开始就不可行。
7. **注**：本机 `prepareLibrary` 曾因「旧 so 已存在则永不覆盖」bug 导致部署旧版 so，拦截失效——排查时必须校验设备 so 与源码一致。

## 4. 统一架构（方案一/二共享）

### 4.1 总体链路

```
物理挂机键(power) 按下
      │
      ▼
mini_shizuku 服务端(原生层 interceptor.c)
  ├─ find_device_with_key(KEY_POWER) → 找到含 power 的设备(本机 event1/gpio-keys)
  ├─ EVIOCGRAB 独占抓取（系统 InputReader 收不到该设备事件）
  ├─ 尝试 setup_uinput()
  │     ├─ 成功 → 回放模式：非 power 事件原样回放到 uinput（不吞键）
  │     └─ 失败 → 纯消费模式：非 power 事件一并丢弃（保底）
  │
  └─ power 事件 → 【目标行为决策状态机】→ 注入
        ├─ 屏幕灭      → 注入唤醒（input keyevent 224 / 26）
        ├─ 屏幕亮+非桌面 → 注入回桌面（am start 拉起 NokiaDesktopActivity）
        └─ 屏幕亮+桌面   → 注入锁屏（input keyevent 26）
```

### 4.2 决策输入（状态探测）

服务端以 shell（adb 拉起）或 root（libsu 激活）身份执行 `dumpsys` 获取两个状态，由独立「状态线程」轮询缓存（避免按键时现场执行造成延迟）：

| 状态 | 命令 | 解析目标 |
|------|------|----------|
| 屏幕状态 | `dumpsys power 2>/dev/null` | `mWakefulness=Awake/Asleep` |
| 前台窗口 | `dumpsys window windows 2>/dev/null` | `mCurrentFocus=Window{... 组件名}` |

- 前台判断：解析 `mCurrentFocus` 中组件名的**包名前缀**，命中 `io.github.cctyl.nokia` 即为本应用（兼容 debug 后缀 `.debug` 与 release 无后缀）。
- 轮询频率建议 500ms；按键事件到达时直接读缓存，注入延迟 ≈ 0。
- 兼容性风险：各 Android 版本 `dumpsys` 输出格式有差异，解析正则需按版本容错，实机验证为准。

### 4.3 注入通道

| 动作 | 注入方式 | 说明 |
|------|----------|------|
| 回桌面 | `am start -n <pkg>/ru.playsoftware.j2meloader.nokia.NokiaDesktopActivity` | 精确拉起，**不依赖 HOME 归属**（比 `input keyevent 3` 更可靠） |
| 锁屏 | `input keyevent 26`（POWER） | 走 InputManager，不受 evdev grab 影响，触发系统锁屏+熄屏 |
| 唤醒 | `input keyevent 224`（WAKEUP），备选 `26` | 灭屏时注入点亮屏幕；不同 ROM 对注入 power 唤醒支持度不一，需实机验证 |

> 设计决策：**注入统一走 shell 命令**（`am start` / `input keyevent`），方案一、方案二完全复用同一套注入逻辑；uinput 的唯一职责是**非 power 键事件回放**（解决吞音量键），职责单一、逻辑干净。

## 5. 目标行为决策状态机（核心逻辑，已实现）

服务端拦截线程在收到 `power 键按下(DOWN)` 事件后执行（power 的 UP 事件一律消费丢弃）：

```
power DOWN 到达（已被 grab 拦截）
  │
  ├─ 读状态缓存：屏幕是否亮 + 前台是否本应用
  │
  ├─ 屏幕灭(Asleep)
  │     → 注入唤醒：input keyevent 224   （点亮屏幕，显示锁屏/桌面）
  │
  ├─ 屏幕亮(Awake) + 前台非本应用
  │     → 注入回桌面：am start -n .../NokiaDesktopActivity
  │
  └─ 屏幕亮(Awake) + 前台是本应用
        → 注入锁屏：input keyevent 26    （触发系统锁屏+熄屏）
```

要点：
- **双击防抖**：注入间隔离 1s 以上，避免与系统 power 防误触策略冲突导致注入被忽略。
- **长按处理（风险项）**：grab 后系统长按 power 的关机菜单将失效。可选增强：检测 DOWN 后超过 2s 未 UP 视为长按，此时释放 grab 放行原始事件（参考 KeyMapper 的 10 秒安全兜底思路），作为可选迭代项，首版可不做。
- **状态缓存失效兜底**：若 `dumpsys` 解析失败（异常输出），保守默认按「屏幕亮 + 前台非本应用」处理（回桌面，最不易造成困在锁屏）。
- **安全兜底（必做）**：服务进程被 kill/崩溃时要能自动释放 grab（或参考 KeyMapper 长按 power 10 秒紧急退出 SystemBridge），避免 power 键永久失效无法关机。

## 6. 方案一：evdev grab + uinput 回放（推荐）

### 6.1 前提
- 设备 shell 可写 `/dev/uinput`（`setup_uinput()` 成功）。本机已验证满足。

### 6.2 行为
- **非 power 键事件**：原样回放到 uinput 虚拟设备（`virtual-nokia-keypad`），音量键等行为完全不变（当前 `interceptor.c` 已实现该分支）。
- **power 键事件**：进入决策状态机（第 5 节），注入回桌面 / 锁屏 / 唤醒。

### 6.3 与现状代码的差异
现状 `interceptor.c` 已具备 uinput 回放框架，仅需改造 `interceptor_run()` 事件循环中 power 分支：
- 现状：power 事件 → 直接 `LOG("Power key consumed")` 丢弃。
- 改造：power DOWN → 调决策状态机 → `popen()` 执行注入命令；power UP → 丢弃。

## 7. 方案二：纯消费保底 / root 激活（权限升级通道）

### 7.1 方案二（无 uinput 时保底）
- **非 power 键事件**：无法回放，一并丢弃（**已知缺陷：吞同设备音量键**）。
- **power 键事件**：与方案一**完全相同**的决策状态机 + shell 注入，目标行为完整实现。
- UI 应明确提示当前模式（「保底模式：音量键将被占用」），避免用户困惑。

### 7.2 root 激活（权限升级通道，已实现；原「方案三」已取消）

> **定位**：root 不再作为第三种独立拦截方案，而是作为「权限升级通道」——通过
> libsu 以 root 身份拉起 mini_shizuku 服务端，让服务端获得完整权限，从而保证
> 方案一的 uinput 回放必定生效（shell 身份时 `/dev/uinput` 写权限可能不足而降级为方案二）。

- **原理**：`interceptor.c` 本身不区分进程身份，root 与 shell 唯一的差异在于对
  `/dev/uinput`（回放设备创建）与 `/dev/input/*`（grab）的权限。服务端以 root 运行时
  `setup_uinput()` 必定成功 → 自动进入方案一完整回放；权限不足则自动降级方案二。
  因此**拦截逻辑零改动**，root 只是补齐了方案一缺的那一项权限。
- **实现**：
  - `app/build.gradle` 引入 libsu core（jitpack `com.github.topjohnwu.libsu:core:5.2.2`，minSdk 19 ≤ 4.4）；
  - `ShizukuRootFragment`（桌面设置 → mini_shizuku → root 激活）：libsu `Shell` API
    检测 root 权限，并以 root 身份执行 `app_process` 拉起服务端（与 `mini_shizuku.sh` 同参数，
    注入 `-Dapp.package` 供重装后 `pm path` 兜底定位）；
  - `AndroidManifest.xml` 通过 `tools:overrideLibrary="...,com.topjohnwu.superuser"` 绕过
    libsu minSdk 19 与本工程 MIN_SDK=14 的 manifest 合并校验。
- **使用方式**：桌面设置 → mini_shizuku → root 激活（首次会弹 su 授权窗）→ 回到
  「电源键拦截设置」选择方案一即可获得完整回放能力。
- **能力边界**：本通道仅做「权限升级」，不修改 `.kl` 键位映射、不做系统级注入
  （这些扩展点暂不实现）。

## 8. KeyMapper 调研结论（源码证据，已验证）

> 调研对象：`D:\project\KeyMapper`（包名 `io.github.sds100.keymapper`，Kotlin + Rust + C++）。

### 8.1 核心结论
- KeyMapper 拦截 power 键**不是在 Android 框架层**，而是在 **Linux 内核输入子系统（evdev）层**：`EVIOCGRAB` 独占抓取 + uinput 虚拟设备回放。
- **无障碍 `onKeyEvent` 只是辅助检测源**（给音量键等普通按键提供无 root 检测通道），**完全不承担拦电源键**；`BaseAccessibilityService` 相关代码里**没有 POWER 键处理**。
- 专家模式（SystemBridge）**必须以 root 或 shell 身份运行**，通过 JNI 调 Rust 的 `libevdev_manager.so` 完成 grab。

### 8.2 关键源码证据

**证据一：`SystemBridge.kt` —— 必须 root/shell 身份：**
```kotlin
private val processPackageName: String = when (Process.myUid()) {
    Process.ROOT_UID -> "root"
    Process.SHELL_UID -> "com.android.shell"
    else -> throw IllegalStateException("SystemBridge must run as root or shell user")
}
```

**证据二：`grabbed_device.rs` —— 只读 open + grab + uinput 回放（与本项目方案一完全一致）：**
```rust
let file = OpenOptions::new()
    .read(true)                      // 只读！
    .custom_flags(libc::O_NONBLOCK)
    .open(device_path)               // 打开 /dev/input/event*
    ...;
evdev.grab(GrabMode::Grab)          // EVIOCGRAB
let uinput = UInputDevice::create_from_device(&evdev)  // uinput 回放
```

**证据三：`event_loop.rs` —— 消费/回放决策：**
```rust
let consumed = ... callback.on_evdev_event(...) // true=拦截 false=放行
if !consumed {
    grabbed_device.uinput.write_event(...);      // 未消费 → 回放
}
```

### 8.3 对本项目的意义
- 本项目 mini_shizuku（`app_process` + TCP，shell 身份）与 KeyMapper 的 shizuku 模式**权限完全等价**。
- 本项目 `interceptor.c` 走的正是同一条路，且已实机验证可拦截 power 键。

  - `AndroidManifest.xml`：`tools:overrideLibrary` 追加 `com.topjohnwu.superuser` 绕过 minSdk 校验。
- JNI 符号注意：包名 `ru.playsoftware.mini_shizuku.server` 含下划线 → JNI 规则为 `_1`，导出符号为 `Java_ru_playsoftware_mini_1shizuku_server_InterceptorNative_*`。

### 10.2 核心实现细节
- **设备查找**：遍历 `/dev/input/eventX`，用 `EVIOCGBIT(EV_KEY)` 读按键位图匹配 `KEY_POWER`，优先物理按键设备（排除 FN 功能键 / 本方案 uinput 虚拟设备）。
- **独占抓取**：`open(dev_path, O_RDONLY)` + `ioctl(fd, EVIOCGRAB, 1)`（**必须只读**，`O_RDWR` 在 enforcing 下失败）。
- **uinput 回放**：尝试 `setup_uinput()` 创建虚拟设备回放未拦截事件；失败则 `LOGW("uinput unavailable, running in consume-only mode")` 进入纯消费。
- **事件循环**：`read` → power 事件进入决策状态机；非 power 且 `uinput_fd>=0` 则 `emit()` 回放。
- **状态线程**：500ms 轮询 `dumpsys power`（`mWakefulness`）与 `dumpsys window windows`（`mCurrentFocus`）缓存屏幕/前台状态，按键时直接读缓存，注入延迟 ≈ 0。
- **注入通道**：`popen()` 执行 `am start -n .../NokiaDesktopActivity`（回桌面）/ `input keyevent 26`（锁屏）/ `input keyevent 224`（唤醒，失败回退 26）。

### 10.3 排障记录（关键教训）
1. **根因一：设备上部署的是旧版 so** —— 本地新 so 与设备 `/data/local/tmp/libnokiainterceptor.so` 不一致（曾 36356 字节 vs 7136 字节），旧版在 `setup_uinput` 失败后线程直接返回、grab 被释放，拦截形同虚设。**排查必须先核对设备 so 与源码一致**（字符串比对 / 字节数）。
2. **根因二：`prepareLibrary` 不覆盖旧文件** —— `if (out.exists() && out.length() > 0) return true;` 导致旧 so 永不更新。**修复**：手动 `adb push` 覆盖或删除旧文件后重启服务端（后续应加版本号比对强制覆盖）。
3. **根因三：抓错设备** —— 早期抓到 `event5`/`qpnp_pon`（非物理电源键设备），修复后正确抓到 `event1`/`gpio-keys`。

### 10.4 验证方法（复现）
```bash
# 1. 重启服务端（确保加载最新 so）
adb -s <serial> shell "ps | grep app_process | grep -v grep | while read l; do set -- \$l; kill -9 \$2; done; sleep 1; sh /data/local/tmp/mini_shizuku.sh"

# 2. 确认 fd 持有 event1（关键判据：有则 grab 生效）
adb -s <serial> shell "ls -la /proc/<pid>/fd/ | grep event1"

# 3. 清日志后发送启动命令，核对完整日志
adb -s <serial> logcat -c
python -c "import socket;s=socket.create_connection(('127.0.0.1',10500));s.sendall(b'EXEC|INTERCEPTOR_START\n');s.close()"
adb -s <serial> logcat -d -s MiniShizuku:* Interceptor:*
# 期望输出：Found KEY_POWER / uinput replay device created / Interceptor started successfully
```

### 10.5 已知限制
1. **纯消费模式吞掉同设备其它按键**（无 uinput 时）；本机已验证有 uinput，回放模式音量键不吞。
2. **重启后失效**：mini_shizuku 服务与拦截器均不持久化，重启后需重新激活服务（`sh mini_shizuku.sh` 或 root 激活）并开启拦截。
3. **UI 不查询真实运行模式**：设置页保存的是用户选择（方案1/方案2），不读取服务端实际模式（uinput 回放 / 纯消费）。后续可加 `INTERCEPTOR_STATUS` 状态查询命令使二者一致。
4. **拦截开启期间 power 键被吞**：需注入通道（`input keyevent`）或 `INTERCEPTOR_STOP` 恢复系统默认行为。
5. **root 激活依赖 su 授权弹窗**：若设备的 root 管理器（Magisk Manager 等）被隐藏/卸载，su 授权弹窗无法出现，root 激活将失败（shell 通道仍可用）。
