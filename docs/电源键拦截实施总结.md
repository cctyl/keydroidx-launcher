# 电源键拦截（evdev grab）实施总结

> 文档性质：实施总结。记录「按下 power 键导致诺基亚桌面退出」问题的最终解决方案、
> 关键实现、排障过程与已知限制。
> 关联文档：《KeyMapper专家模式拦截power键原理分析.md》（调研结论，本方案即按其思路实现）。

---

## 1. 问题背景

- 本应用是诺基亚风格安卓桌面（`NokiaDesktopActivity`），作为系统默认 Home 运行。
- 用户反馈：**按下物理 power 键后，桌面进程退出并回到系统内置桌面**。
- 原因：power 键由系统 `PhoneWindowManager` 处理，App 层无法拦截（framework 保留键）。
- 目标是像 KeyMapper 专家模式一样，在内核输入层（evdev）用 `EVIOCGRAB` 事前拦截 power 键。

## 2. 最终方案

利用项目已有的 **mini_shizuku**（`app_process` + TCP，shell 身份）通道：

1. 服务端以 shell 身份加载原生库 `libnokiainterceptor.so`。
2. 原生层枚举 `/dev/input`，找到含 `KEY_POWER` 的设备（本机为 `event5`/`qpnp_pon`）。
3. 对该设备执行 `EVIOCGRAB` 独占抓取 → 系统 InputReader 收不到该设备任何按键事件。
4. 事件循环中消费掉 power 键（DOWN/UP 都丢弃），即「纯消费模式」。
5. 桌面设置 → mini_shizuku → 新增「电源键拦截」开关控制启停。

**效果**：开启后按 power 键，桌面不再退出，日志出现 `Power key consumed`（纯消费模式
下由丢弃逻辑体现，详见代码）。

## 4. 核心实现细节

### 4.1 设备查找

```c
// 遍历 /dev/input/eventX，用 EVIOCGBIT(EV_KEY) 读按键位图，匹配 KEY_POWER
if (test_bit(KEY_POWER, key_bitmask)) { ... 命中 ... }
```

### 4.2 独占抓取

```c
power_key_fd = open(dev_path, O_RDWR);      // shell 属于 input 组，可打开
ioctl(power_key_fd, EVIOCGRAB, 1);          // grab 后系统收不到该设备事件
```

### 4.3 uinput 回放（可选，需权限）

```c
// 尝试创建 uinput 虚拟设备，把未拦截事件原样回放给系统；
// 失败则进入纯消费模式（本机 shell 无 /dev/uinput 写权限，走此路径）
uinput_fd = setup_uinput(power_key_fd);
if (uinput_fd < 0) LOGW("uinput unavailable, running in consume-only mode");
```

### 4.4 事件循环

```c
while (is_running) {
    read(power_key_fd, &ev, sizeof(ev));
    if (ev.type == EV_KEY && ev.code == KEY_POWER) {
        // 消费掉 power 键（按下/抬起都丢弃）
    } else if (uinput_fd >= 0) {
        emit(uinput_fd, ev.type, ev.code, ev.value);  // 有 uinput 时回放其它键
    }
}
```

### 4.5 JNI 符号命名

包名 `ru.playsoftware.mini_shizuku.server` 中 `mini_shizuku` 含下划线，JNI 规则为
下划线 → `_1`，故导出符号为 `Java_ru_playsoftware_mini_1shizuku_server_InterceptorNative_*`。

## 5. 排障过程（关键教训）

> 用户多次反馈「开启了但还是退出」。反复排查后定位到两个根因：

### 5.1 根因一：设备上部署的是旧版 so

- 现象：本地新编译 so 为 **36356 字节**，设备上 `/data/local/tmp/libnokiainterceptor.so`
  却只有 **7136 字节**，缺少 `Power key consumed` / `uinput unavailable` 等新逻辑字符串。
- 后果：旧版 so 在 `setup_uinput` 失败后**线程直接返回**，grab 被释放，power 键照常传递，
  拦截形同虚设。
- 证据链：
  1. 服务端日志只到 `Failed to open uinput`，没有 `Interceptor started successfully`；
  2. 进程 fd 列表里没有 `event5`（grab 未持有）；
  3. 字符串比对确认设备 so 与源码不一致。

### 5.2 根因二：`prepareLibrary` 不会自动覆盖旧文件

```java
// InterceptorNative.java
if (out.exists() && out.length() > 0) {
    return true;   // ★ 文件已存在（哪怕旧版）就直接跳过，永不重新解压
}
```

- 只要旧 so 存在于 `/data/local/tmp`，服务端永远加载旧版。
- **修复**：手动 `adb push` 新版 so 覆盖后再重启服务端，或先删除旧文件再触发拦截。

### 5.3 验证方法（可供复现）

```bash
# 1. 重启服务端（确保加载最新 so）
adb -s <serial> shell "ps | grep app_process | grep -v grep | while read l; do set -- \$l; kill -9 \$2; done; sleep 1; sh /data/local/tmp/mini_shizuku.sh"

# 2. 确认 fd 持有 event5（关键判据：有则 grab 生效）
adb -s <serial> shell "ls -la /proc/<pid>/fd/ | grep event5"

# 3. 清日志后发送启动命令，核对完整日志
adb -s <serial> logcat -c
python -c "import socket;s=socket.create_connection(('127.0.0.1',10500));s.sendall(b'EXEC|INTERCEPTOR_START\n');s.close()"
adb -s <serial> logcat -d -s MiniShizuku:* Interceptor:*
# 期望输出：Found KEY_POWER / Interceptor started successfully
```

## 6. 已知限制与注意事项

1. **纯消费模式吞掉同设备其它按键**：本机 shell 无法写 `/dev/uinput`，进入纯消费模式，
   `event5` 上的音量键等也会被一并丢弃。若需保留其它按键，需要 root 或改走其它注入通道。
2. **系统无法用 power 键熄屏/唤醒**：拦截开启期间 power 事件被吞，电源管理不受按键控制，
   需通过 `adb shell input keyevent 26`（注入走 InputManager，不受 grab 影响）或
   `INTERCEPTOR_STOP` 恢复正常。
3. **重启后失效**：mini_shizuku 服务与拦截器均不持久化，设备重启后需重新
   `sh mini_shizuku.sh` 并在设置中开启拦截。
4. **开关状态仅内存**：`ShizukuFragment.interceptorEnabled` 重启后默认关闭，与真实服务状态
   可能不一致（显示已关闭但实际仍拦截）。后续可加状态查询命令。

## 7. 后续改进建议

- **状态查询命令**：服务端增加 `INTERCEPTOR_STATUS` 返回 is_running，UI 据此回显真实状态。
- **保留其它按键**：想办法写 `/dev/uinput`（root），或只 grab 后按需回放音量键。
- **自动启动**：桌面启动时探测服务在线则自动开启拦截（需先解决状态一致性）。
- **安全兜底**：参考 KeyMapper 的长按 power 10 秒释放 grab 机制，防止异常退出后 power 键永久失效。
