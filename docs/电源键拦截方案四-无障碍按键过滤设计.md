# 电源键拦截方案四：无障碍按键过滤（跨版本兜底）

> 文档性质：**设计稿（待审核）**。提出用无障碍服务按键过滤实现「挂机键语义」的方案，
> 作为 evdev grab 方案（方案一/二）在跨版本、无 adb 场景下的兜底与补充。
> 关联文档：
> - 《电源键拦截分级方案设计.md》—— 方案一/二/三的定义与目标行为状态机（本文档沿用其「目标行为」与「决策状态机」定义）。
> - 《KeyMapper专家模式拦截power键原理分析.md》—— 调研结论：KeyMapper 拦截 power 键有两套机制，专家模式用 evdev grab，普通模式用无障碍按键过滤。本文档采用其普通模式机制。
> - 《电源键拦截实施总结.md》—— 方案一/二当前实现基线。

## 1. 为什么需要方案四（背景与定位）

### 1.1 方案一/二的既有依赖与脆弱性

方案一（uinput 回放）与方案二（纯消费）依赖 **mini_shizuku + evdev grab**，存在以下问题：

| 依赖点 | 说明 | 风险 |
|--------|------|------|
| adb 手动启动服务 | 服务端需用户在电脑上 `adb push mini_shizuku.sh && adb shell sh` 拉起 | 手机重启即失效，普通用户无法自启 |
| shell 身份 + SELinux | grab 需 shell 域对 input 设备有权限 | 4.4（permissive）可行；5.0+（enforcing）**必须只读打开**（`O_RDONLY`），不同 ROM 策略不一 |
| 写 `/dev/uinput` | uinput 回放需 shell 属 uhid 组 | 部分设备 shell 无 uhid 组 → 只能方案二（吞音量键） |
| 安全兜底 | grab 后需可靠的释放机制，否则 power 键永久失效 | 进程被杀/崩溃时可能残留 grab |

### 1.2 方案四的定位

**无障碍按键过滤**是 Android 提供的**公开系统 API**：

- 无需 root、无需 shell 身份、无需 adb、无需独立服务进程；
- 由用户自主在「系统设置 → 无障碍」开启，重启后**依然生效**（系统级绑定）；
- 从 Android 4.4（API 14）到 13（API 33）行为一致（`FLAG_REQUEST_FILTER_KEY_EVENTS` 为 API 14+ 公开常量）；
- **KeyMapper 已在这台安卓13 设备上实测可用**（其无障碍服务 `capabilities=105` 含
  `CAPABILITY_CAN_REQUEST_FILTER_KEY_EVENTS`，用户已确认能拦截挂机键）。

故方案四定位为：**跨版本、免 adb、免服务进程的「挂机键语义」兜底实现**，与方案一/二
（依赖开发期 adb 的深度拦截）互补。两者共享同一套「目标行为决策状态机」。

## 2. 目标行为（与方案一/二完全一致）

沿用《电源键拦截分级方案设计》定义：「挂机键」= 物理电源键（`KEYCODE_POWER`=26）：

| 场景 | 用户按挂机键后期望行为 |
|------|------------------------|
| 屏幕亮 + 处于任意应用 | **回到诺基亚桌面 `NokiaDesktopActivity`**，不熄屏 |
| 屏幕亮 + 已处于诺基亚桌面主界面 | **锁屏（熄屏）** |
| 屏幕灭 / 已锁屏 | **唤醒（点亮屏幕）** |

> 与方案一/二差异：方案一/二在**内核 evdev 层**拦截（grab）；方案四在 **InputDispatcher
> 层**（无障碍按键过滤）拦截。两者都在 `PhoneWindowManager` 之前，效果等价。

## 3. 原理：无障碍按键过滤如何截获 power 键

Android 按键事件分发链：

```
物理按键
  → InputReader → InputDispatcher
      ├─ ★ Accessibility 按键过滤（KEY_FILTER，本方案在此拦截）
      │     若无障碍服务声明 FLAG_REQUEST_FILTER_KEY_EVENTS，
      │     事件先经 sendKeyEventToAccessibility 发给服务
      │     → 服务 onKeyEvent() 返回 true = 消费（系统收不到）★
      │     → 返回 false = 放行给系统
      ├─ PhoneWindowManager.interceptKeyBeforeQueueing（系统保留键，如 power/endcall）
      └─ Activity.dispatchKeyEvent()（App 层）
```

- 无障碍按键过滤发生在 **InputDispatcher 层、早于 PhoneWindowManager**，因此
  `KEYCODE_POWER` / `KEYCODE_ENDCALL` 这类系统保留键**也能被截获**——这正是 KeyMapper
  能用无障碍服务拦截挂机键的原因，也是本方案的理论依据。
- 服务 `onKeyEvent(KeyEvent event)` 返回 `true` 表示**消费**：事件不再传给系统
  （不触发系统默认熄屏/锁屏逻辑）；返回 `false` 则原样放行。

### 3.1 关键 API 与版本

| API | 用途 | 最低版本 |
|-----|------|----------|
| `AccessibilityServiceInfo.FLAG_REQUEST_FILTER_KEY_EVENTS` | 请求接收所有按键事件（含 power） | API 14 |
| `android:canRequestFilterKeyEvents="true"`（XML 声明） | 系统设置页可见该能力 | API 16（Android 4.1） |
| `AccessibilityService.onKeyEvent()` | 收到按键并决定消费/放行 | API 14 |
| `PowerManager.isInteractive()` | 判断屏幕亮/灭 | API 20（4.4 用 `isScreenOn()`，API 20 前） |
| `ActivityManager.getRunningTasks()` / `UsageStatsManager` | 获取前台包名 | API 21 / 21（4.4 用 getRunningTasks 兜底） |
| `DevicePolicyManager.lockNow()` | 锁屏（需设备管理器） | API 8 |
| `KeyguardManager.requestDismissKeyguard()` | 解锁 | API 26 |

> 兼容性约束：本项目 `MIN_SDK=14`（Android 4.4）。前台探测在 4.4 用
> `ActivityManager.getRunningTasks(1)`（4.4 无权限限制），5.0+ 改用
> `UsageStatsManager` 或 `getRunningTasks` 加 `GET_TASKS` 权限容错；屏幕状态用
> `PowerManager` 反射 `isScreenOn()`（4.4）与 `isInteractive()`（5.0+）双路径。

## 4. 总体架构

```
┌──────────────────────────────────────────────────────────────┐
│                        诺基亚桌面 App 进程                        │
│                                                                │
│  NokiaAccessibilityService（无障碍服务，常驻系统）                 │
│   ├─ onKeyEvent()：收到 KEYCODE_POWER                          │
│   │     ├─ 开关未开（SharedPreferences 关闭）→ return false 放行 │
│   │     └─ 开关开启 → 【目标行为决策状态机】→ 注入动作             │
│   │            ├─ 屏幕灭      → 唤醒（KeyguardManager.requestDismiss / AM 唤醒）│
│   │            ├─ 屏幕亮+非桌面 → 回桌面（startActivity NokiaDesktopActivity）│
│   │            └─ 屏幕亮+桌面   → 锁屏（DevicePolicyManager.lockNow）│
│   │            └─ 返回 true（消费事件，系统不再处理 power）       │
│   └─ 状态探测：PowerManager 屏幕状态 + 前台包名（各版本兼容）       │
│                                                                │
│  NokiaDesktopSettingsFragment                                   │
│   └─ 「挂机键拦截（无障碍）」开关：写 SharedPreferences +          │
│        检测无障碍是否启用，未启用则跳转系统无障碍设置引导          │
└──────────────────────────────────────────────────────────────┘
```

### 4.1 注入通道（无需 root/shell，全部应用内 API）

| 动作 | 注入方式 | 说明 |
|------|----------|------|
| 回桌面 | `startActivity(Intent(NokiaDesktopActivity))` + `NEW_TASK/SINGLE_TOP/REORDER_TO_FRONT` | 与方案一/二 `am start` 等价，应用内直接拉起 |
| 锁屏 | `DevicePolicyManager.lockNow()`（需设备管理器，项目已有 `NokiaDeviceAdminReceiver`） | 立即锁屏+熄屏，与 `input keyevent 26` 等价 |
| 唤醒 | `PowerManager.wakeUp()`（需 `WAKE_LOCK`+`DEVICE_POWER`）或无障碍 `performGlobalAction(GLOBAL_ACTION_...)` | 锁屏态下按挂机键：先 `wakeUp` 点亮 → 显示锁屏/桌面 |

> 锁屏依赖设备管理器：项目已有 `NokiaDeviceAdminReceiver`（`force-lock` 权限，锁屏页在用），
> 直接复用，无新增权限。

## 5. 目标行为决策状态机（与方案一/二相同）

服务在 `onKeyEvent` 收到 `KEYCODE_POWER` 的 `ACTION_DOWN` 后执行（UP 一律消费丢弃，
避免系统处理 UP）：

```
KEYCODE_POWER DOWN 到达（无障碍已拦截）
  │
  ├─ 读状态：屏幕是否亮 + 前台是否本应用
  │
  ├─ 屏幕灭(Asleep)
  │     → 注入唤醒：wakeUp() + requestDismissKeyguard（点亮并解锁）
  │
  ├─ 屏幕亮(Awake) + 前台非本应用
  │     → 注入回桌面：startActivity(NokiaDesktopActivity)
  │
  └─ 屏幕亮(Awake) + 前台是本应用
        → 注入锁屏：DevicePolicyManager.lockNow()
```

要点（沿用分级方案）：
- **双击防抖**：注入间隔 ≥1s，避免与系统防误触策略冲突。
- **状态缓存失效兜底**：前台探测失败时保守按「屏幕亮 + 非本应用」→ 回桌面（最不易困在锁屏）。
- **开关为唯一总闸**：`SharedPreferences("power_key_interceptor_enabled")`，关闭时 `onKeyEvent` 直接返回 false 完全放行。

## 6. 关键实现细节

### 6.1 无障碍服务声明（XML）

`app/src/main/res/xml/nokia_accessibility_config.xml`：

```xml
<accessibility-service xmlns:android="http://schemas.android.com/apk/res/android"
    android:description="@string/nokia_a11y_desc"
    android:accessibilityEventTypes="typeWindowStateChanged"
    android:accessibilityFeedbackType="feedbackGeneric"
    android:notificationTimeout="0"
    android:canRetrieveWindowContent="false"
    android:canRequestFilterKeyEvents="true" />
```

`AndroidManifest.xml` 注册（复用项目现有无障碍服务模式）：

```xml
<service
    android:name=".nokia.NokiaAccessibilityService"
    android:exported="false"
    android:permission="android.permission.BIND_ACCESSIBILITY_SERVICE">
    <intent-filter>
        <action android:name="android.accessibilityservice.AccessibilityService" />
    </intent-filter>
    <meta-data
        android:name="android.accessibilityservice"
        android:resource="@xml/nokia_accessibility_config" />
</service>
```

> 注：`NokiaKioskService`（《挂机键拦截方案设计文档》的方案 B，事后拉回）已存在，
> 本方案四为**事前拦截**，两者可共存：方案四消费 power 键 → 系统根本不会切走 → 方案 B 不触发。

### 6.2 服务端核心（`NokiaAccessibilityService.java` 骨架）

```java
public class NokiaAccessibilityService extends AccessibilityService {

    @Override
    protected void onServiceConnected() {
        AccessibilityServiceInfo info = new AccessibilityServiceInfo();
        info.eventTypes = AccessibilityEvent.TYPE_WINDOW_STATE_CHANGED;
        info.feedbackType = AccessibilityServiceInfo.FEEDBACK_GENERIC;
        info.flags = AccessibilityServiceInfo.FLAG_REQUEST_FILTER_KEY_EVENTS; // ★ 关键
        setServiceInfo(info);
    }

    @Override
    public boolean onKeyEvent(KeyEvent event) {
        // 总闸：未开启则完全放行
        if (!isInterceptorEnabled()) return false;
        if (event.getKeyCode() != KeyEvent.KEYCODE_POWER) return false;

        if (event.getAction() == KeyEvent.ACTION_DOWN) {
            handlePowerKeyDown();
        }
        // DOWN/UP/REPEAT 全部消费，系统收不到 power 事件
        return true;
    }

    private void handlePowerKeyDown() {
        // 防抖 + 状态机：见第 5 节
        // 状态探测：PowerManager 屏幕 + 前台包名（各版本兼容）
        // 注入：回桌面 / 锁屏 / 唤醒
    }
}
```

### 6.3 状态探测（版本兼容）

```java
// 屏幕是否亮：4.4 用 isScreenOn()（反射），5.0+ 用 isInteractive()
@SuppressWarnings("deprecation")
boolean isScreenOn() {
    PowerManager pm = (PowerManager) getSystemService(POWER_SERVICE);
    if (Build.VERSION.SDK_INT >= 20) return pm.isInteractive();
    try {
        return (Boolean) PowerManager.class.getMethod("isScreenOn").invoke(pm);
    } catch (Exception e) { return true; } // 保守默认亮
}

// 前台包名：4.4 用 getRunningTasks（无权限限制）；5.0+ 用 UsageStatsManager（需 PACKAGE_USAGE_STATS）
boolean isForegroundSelf() {
    String top = ...; // 解析 getRunningTasks(1) 或 UsageStatsManager.queryEvents 最新
    return top != null && top.startsWith("io.github.cctyl.nokia"); // 兼容 debug/release
}
```

### 6.4 桌面设置入口

在 `NokiaDesktopSettingsFragment` 增加「挂机键拦截（无障碍）」项：

- **开启时**：写 `SharedPreferences` + 检测 `isAccessibilityServiceEnabled()`，
  未启用则跳转 `Settings.ACTION_ACCESSIBILITY_SETTINGS` 引导用户开启；
- **关闭时**：写 `SharedPreferences`，服务仍在运行但 `onKeyEvent` 直接放行；
- 状态回显：服务是否已启用（`Settings.Secure.ENABLED_ACCESSIBILITY_SERVICES` 匹配包名/服务名）。

## 7. 兼容性与风险

### 7.1 兼容性

| 版本 | 支持 | 说明 |
|------|------|------|
| Android 4.4（API 19） | ✅ | FLAG_REQUEST_FILTER_KEY_EVENTS（API 14）、isScreenOn 反射、getRunningTasks 可用 |
| Android 5~12 | ✅ | isInteractive、UsageStatsManager 或 GET_TASKS |
| Android 13 | ✅ | KeyMapper 已实测同类机制可拦截 power 键 |
| 无 root / 无 adb / SELinux Enforcing | ✅ | 系统公开 API，无特权依赖 |

### 7.2 风险与对策

| # | 风险 | 对策 |
|---|------|------|
| 1 | 用户关闭无障碍服务后拦截失效 | 设置页显示真实服务状态；关闭即放行（降级为系统默认 power 行为，无副作用） |
| 2 | 个别 ROM 对 filter key events 权限收紧（收不到 power 键） | 兜底：监听 `TYPE_WINDOW_STATE_CHANGED` + 事后拉回（复用 `NokiaKioskService` 思路），双保险 |
| 3 | 注入唤醒/锁屏 API 各版本差异 | 多路尝试（wakeUp → requestDismissKeyguard → performGlobalAction），失败按保守策略回桌面 |
| 4 | 消费 power 键后系统长按关机菜单失效 | 检测 DOWN 持续 >2s 视为长按 → 返回 false 放行（交给系统），首版可后置 |
| 5 | 无障碍服务被杀/未自启 | 服务系统级绑定，通常自动重启；配合桌面启动时检测引导开启 |
| 6 | 与方案一/二同时开启冲突 | 设置页两者互斥（开启其一提示关闭另一）；决策状态机同一套，不会重复注入 |

## 8. 与方案一/二/三的关系

| 方案 | 通道 | 权限依赖 | 跨版本 | 定位 |
|------|------|----------|--------|------|
| 方案一 | evdev grab + uinput 回放 | mini_shizuku（adb）+ shell + uhid 组 | 需 O_RDONLY 兼容 | 深度拦截，不吞音量键 |
| 方案二 | evdev grab 纯消费 | mini_shizuku（adb）+ shell | 同上 | 深度拦截，吞音量键 |
| 方案三 | root 增强 | root | 最强 | 预留扩展 |
| **方案四** | **无障碍按键过滤** | **仅用户开启无障碍** | **4.4~13 通用** | **免 adb、用户可自启，跨版本兜底** |

> 推荐组合：**方案四为主（用户体验好、免 adb）+ 方案一为增强**（开发期/有权限机深度拦截）。
> 方案四不依赖 mini_shizuku，可直接在本项目落地，与现有「电源键拦截」开关并行。

## 10. 验证计划（本机：安卓13，C65GA202401021974）

1. 安装最新 APK → 桌面设置开启「挂机键拦截（无障碍）」→ 跳转系统无障碍设置，启用服务。
2. `adb shell am start -n com.android.settings/.Settings` 进设置（模拟任意应用）。
3. 按物理挂机键 → 期望：**回到诺基亚桌面，且不熄屏**。
4. 在诺基亚桌面按挂机键 → 期望：**锁屏（熄屏）**。
5. 锁屏后按挂机键 → 期望：**唤醒点亮**。
6. 关闭开关 → 按挂机键 → 期望：恢复系统默认行为（熄屏/唤醒）。
7. 连续按 20 次 → 无崩溃、无重复注入、开关状态不漂移。
8. 重启手机 → 无障碍服务自动生效，无需 adb（对比方案一需重新 `sh mini_shizuku.sh`）。

## 11. 待确认问题（评审点）

1. **Android 13 无障碍过滤对 power 键的完整事件流**（DOWN/UP/REPEAT 是否都可达、
   长按是否触发系统拦截）—— 需实机验证，必要时在 `onKeyEvent` 打印日志确认。
2. **锁屏注入通道**：`DevicePolicyManager.lockNow()` 需设备管理器已激活；
   若未激活，降级用 `KeyguardManager` 或 `performGlobalAction(GLOBAL_ACTION_LOCK_SCREEN)`。
3. **唤醒注入**：`PowerManager.wakeUp()` 需 `android.permission.WAKE_LOCK` 且
   `DEVICE_POWER` 权限（普通应用无）—— 若不可用，改用
   `KeyguardManager.requestDismissKeyguard()` 或无障碍
   `performGlobalAction(GLOBAL_ACTION_DISMISS_KEYGUARD)` 等公开通道。
4. **与现有 `NokiaKioskService`（方案 B 事后拉回）的共存策略**：建议方案四开启后
   自动停用方案 B，避免双路竞争。
